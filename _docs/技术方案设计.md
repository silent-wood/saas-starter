## 1. 文档目的与范围

本文档回答「怎么实现」：给出总体架构、前端技术方案、后端技术方案、专项横切设计与里程碑映射。**组织方式为整体设计**：按层次与模块展开，页面级设计以前端篇的「路由 × 页面 × 接口 × 权限矩阵」覆盖，不逐页成文。

范围 = 需求文档 v1.1 全部 v1 交付项（M1–M6）；后续版本池（WebSocket、OAuth、Webhook、真实支付网关等）仅标注扩展点，不展开设计。

### 2.2 关键数据流

| 链路 | 路径 |
|------|------|
| 常规请求 | 浏览器 → CF CDN → CORS 白名单校验 → NestJS → 租户守卫注入 tenantId → Prisma → Postgres |
| 异步任务 | 业务 Service → BullMQ → Upstash → Worker 消费（邮件 / 文档向量化 / 续费重试 / 对账 / 清理） |
| AI 问答 | 前端 POST /ai/ask（SSE）→ 配额校验 → pgvector 语义检索 → LLM 流式 → SSE 逐 token 转发 → 落库引用 |
| 文件上传 | 前端请求预签名 URL → R2 直传 → 回调确认 → 元数据入库 → 计入存储配额 |
| 实时推送 | 业务事件 → SSE 广播服务（按 tenantId 分组）→ 浏览器 EventSource 接收 → 前端提示条/通知 |
| 支付（模拟） | 前端带 Idempotency-Key 调订阅 → 幂等表判重 → MockGateway.charge → 账单落库 → 事件/通知 → 权益联动 |

### 2.3 技术栈确认（构建前以官方最新稳定版复核）

与需求文档第 3 章一致，本节明确**落库版本锚点与理由**：

| 层 | 选型 | 版本锚点 | 决策理由（含被否选项） |
|----|------|---------|----------------------|
| 前端框架 | React + React Router | ^19 / ^7 | SPA 纯静态部署最优；否 Next.js（失去 SSR 无意义） |
| UI | Ant Design 5 + @ant-design/pro-components | ^5 / 最新 | AntD 中后台组件覆盖全（表格/表单/流式列表）；ProComponents（ProLayout/ProTable/ProForm）独立于 umi 可在 Vite 直接使用，压降 12 屏样板代码。**不用 UmiJS**：作品集定位需展示自建工程骨架（路由/构建/状态/权限均为自有设计），且 umi 对 React 19 支持滞后 |
| 构建 | Vite | ^6 | TS 工程化 + 静态产物 |
| 客户端状态 | Zustand | ^5 | 轻量，仅存会话/UI 态 |
| 服务端状态 | TanStack Query | ^5 | 缓存/重试/失效模型天然适配 CRUD + 权限变化 |
| 表单校验 | RHF + Zod | ^7 / ^3 | Zod schema 与 shared 包同源复用 |
| HTTP | Axios | ^1.7 | 拦截器成熟（刷新 token、错误归一） |
| 后端框架 | NestJS | ^11 | 模块化 + DI + 守卫/拦截器体系支撑横切设计 |
| ORM | Prisma | ^6 | schema 即事实源；Client Extension 实现租户过滤注入 |
| 数据库 | PostgreSQL + pgvector | 16+ | 业务 + 向量一库双用，免额外向量库 |
| 队列/缓存 | BullMQ + Upstash | 最新 | serverless Redis 免运维，免费档够演示 |
| AI SDK | Vercel AI SDK | 最新 | 流式 API 统一，可换底层模型 |
| 邮件 | Resend SDK（HTTPS API）+ nodemailer（本地 SMTP 兜底） | 最新 | **走 HTTPS API 而非 SMTP**：Render 免费档自 2025-09-26 起封锁出站 25/465/587，SMTP 方案在免费档静默超时；HTTPS API 走 443，任何托管平台都不封。`MAIL_PROVIDER` 策略切换 resend / smtp / mock |
| 部署 | CF Pages + Render/Railway | — | 境外免备案，免费档组合 |

> 全栈纪律（来自工程规范，前后端通用）：表名/字段名 snake_case；API 统一响应 `{ success, data, message, timestamp }`；错误 `{ success: false, error: { code, message, details } }`；密码 bcrypt cost ≥ 12；金额一律以**分**存储计算；SQL 一律参数化（Prisma 天然满足）。

## 4. 前端技术方案

### 4.1 应用骨架

- **入口装配**：`QueryClientProvider → RouterProvider → AntD ConfigProvider（zhCN）→ App 全局错误边界`。
- **布局**：`/app` 布局采用 **ProLayout**（@ant-design/pro-components，独立组件库、不依赖 umi）：侧边栏/顶栏/通知铃铛/租户切换统一由其 slot 组装，菜单项按权限矩阵过滤渲染。
- **路由**：React Router v7 `createBrowserRouter`，两级布局：

```
/                       # 公共布局（无侧边栏）
├─ /login  /register  /forgot-password
├─ /reset-password?token=  /verify-email?token=
/app                    # AppLayout（顶栏+侧边栏+通知铃铛+租户切换）
├─ /app/dashboard                # 02 工作台            member+
├─ /app/resources               # 03 列表+新建         member+
│  └─ /app/resources/:id        # 04 详情/附件          member+
├─ /app/trash                   # 05 回收站            owner/admin
├─ /app/members                 # 06 成员管理          owner/admin（member 只读列表）
├─ /app/ai                      # 07 AI 助手           member+
├─ /app/billing                 # 08 订阅+模拟支付     owner
├─ /app/billing/invoices        # 09 账单中心          owner
├─ /app/notifications           # 10 通知中心+偏好     member+（偏好部分个人级）
├─ /app/audit                   # 11 审计日志          owner/admin
├─ /app/settings                # 12 租户设置          owner/admin
└─ /app/me                      # 12 个人中心          member+（资料/改密/导出/注销）
```

- **懒加载**：`/app` 下每页 `React.lazy` + 路由级 Suspense（AntD Spin 占位）；首屏只载 login/dashboard chunk。
- **路由守卫**：`<RequireAuth>`（无 token → /login，带 redirect 回跳）与 `<RequireRoles roles={...}>`（不足 → 全局 403 页）。

|---|--------------|---------|---------|-----------|

| 05 | 回收站 | GET /trash、POST /trash/:id/restore、DELETE /trash/:id | owner/admin | 剩余天数倒计时、恢复/彻底删除 |

### 4.3 状态管理分层（职责边界）

| 类别 | 归属 | 内容 |
|------|------|------|
| 服务端状态 | TanStack Query | 一切来自接口的数据。Query Key 约定：`[tenantId, 'resources', filters]`——**租户切换即换 key，缓存天然隔离，防跨租户脏缓存**。变更统一 `invalidateQueries` |
| 会话状态 | Zustand `sessionStore` | access token（内存）+ refresh token（httpOnly cookie 由后端管理，前端不落 localStorage）、当前用户、当前租户 id、角色 |
| UI 状态 | Zustand `uiStore` + 组件局部 | 主题色（租户品牌主色）、SSE 连接状态、全局断网提示、变更提示条 |

### 4.4 认证与会话（前端侧）

- **Token 策略**：access token（15 分钟）仅内存；refresh token 走 httpOnly + SameSite=Strict cookie，前端不可读——XSS 无法窃取长效凭证。
- **静默刷新**：Axios 响应拦截器捕获 401（错误码 `TOKEN_EXPIRED`）→ 单飞（去重并发刷新）调 `POST /auth/refresh` → 重放原请求；刷新失败 → 清 session → 跳 /login。
- **登出**：调 `POST /auth/logout`（后端吊销 refresh token + 清 cookie）+ 前端清 store。

### 4.5 请求层与错误归一

- 单一 Axios 实例 `baseURL = import.meta.env.VITE_API_BASE_URL`；请求拦截器注入 `Authorization: Bearer` 与 `X-Tenant-Id`（当前租户）。
- 响应拦截器统一解包 `{ success, data }`；失败映射为业务异常 `ApiError { code, message, details }`，按错误码路由处理：

| 错误码 | 前端行为 |
|--------|---------|
| TOKEN_EXPIRED | 触发静默刷新重放 |
| FORBIDDEN / ROLE_DENIED | 403 页或按钮级提示 |
| TENANT_MISMATCH / RESOURCE_NOT_FOUND | 提示无权限或不存在（越权不暴露存在性） |
| RATE_LIMITED | 提示稍后重试（读 Retry-After） |
| QUOTA_EXCEEDED_AI / _STORAGE / _SEATS | 定向升级引导弹窗（链到 /app/billing） |
| SUBSCRIPTION_STATE_INVALID | 订阅页刷新状态 |

- **SSE 客户端封装**：`createEventStream(url, { token, tenantId })` 基于 `fetch` + ReadableStream（EventSource 无法带 header），内部处理 401 重连、指数退避（1s/2s/…30s 封顶）、心跳超时（90s 无事件重连）；`onEvent` 按 `type` 分发：`notification`（未读+1、列表插入）、`resource.changed`（顶部「数据已变更」提示条 + invalidate）、`ai.answer`（问答页 token 追加）。轮询兜底：SSE 断开期间通知 30s 轮询。

### 4.6 权限渲染（按钮级）

- `usePermission()` hook 返回 `{ role, can: (action) => boolean }`；`<AuthButton roles={['owner']}>`、`v-can` 工具函数统一控制按钮 disabled/hidden。
- 权限矩阵常量放 `packages/shared`（与后端守卫同源），避免两端规则漂移。核心矩阵：

| 操作 | member | admin | owner |
|------|--------|-------|-------|
| 资源增删改 | ✅ | ✅ | ✅ |
| 上传附件 | ✅ | ✅ | ✅ |
| 回收站管理 / 审计查看 | ❌ | ✅ | ✅ |
| 邀请 / 调角色 / 禁用 / 移除 | ❌ | ✅（admin 不能改 owner） | ✅ |
| owner 转让 | ❌ | ❌ | ✅ |
| 订阅 / 退款 / 账单 | ❌ | ❌ | ✅ |
| 租户设置 | ❌ | ✅ | ✅ |

### 4.7 关键页面设计要点

- **列表与表单页基建**：03/06/09/11 等 CRUD 列表页统一用 **ProTable**（分页/过滤/工具栏开箱即用，请求对接 TanStack Query 封装），新建/编辑弹窗用 **ProForm** + Zod 校验桥接——样板代码量对标 umi 系脚手架，但工程骨架仍为自有设计。
- **07 AI 助手（流式渲染）**：问答区虚拟滚动；SSE token 到达即 `flushSync` 局部追加（避免整页重渲）；回答完成后展开「引用来源」折叠面板（片段 + 原文跳转）；文档列表项显示 `processing → ready/failed` 状态轮询（TanStack Query refetchInterval，SSE ready 事件优先触发）。
- **08 订阅页（状态机可视化）**：当前订阅状态徽标 + 状态流转示意（none→trialing→active→past_due→canceled/expired，只进不退）；宽限期显著倒计时条；模拟支付弹窗展示本次生成的 `Idempotency-Key`（演示资金安全能力，评审亮点）。
- **02 工作台 / 用量卡**：ECharts 单图（演示验证点）+ 三配额进度条（席位/存储/AI），≥80% 橙色、100% 红色 + 升级引导。
- **空态/异常态**：全局 `EmptyState`（图示+引导新建）、`ErrorBoundary` 兜底页、网络断开全局提示条——与用户手册第 4 节「界面状态说明」一一对应。

### 4.8 前端横切

- **构建**：Vite manualChunks 分组（react / antd / echarts / 业务）；产物 ≤ 主流 3G 可接受（演示级不设硬指标，CI 打印体积报告）。
- **环境变量**：仅 `VITE_API_BASE_URL` 等公开前缀变量；构建期注入。
- **代码质量**：ESLint（typescript-eslint + react-hooks 规则）+ Prettier，CI 门禁。
- **可访问性**：AntD 默认焦点管理 + 表单 label 关联；键盘可达（评审演示项，不做全量 WCAG 承诺）。

## 5. 后端技术方案

### 5.1 分层与模块划分

严格 `Controller（HTTP 适配）→ Service（业务/事务边界）→ Repository（Prisma 封装）`：

| NestJS 模块 | 职责 | 关键服务 |
|------------|------|---------|
| auth | 注册/验证/登录/刷新/登出/找回密码 | AuthService、TokenService |
| users | 个人资料、改密、导出、注销 | UsersService |
| tenants | 租户创建（随注册）、设置、切换 | TenantsService |
| members / invitations | 成员生命周期、邀请接受 | MembersService |

### 5.2 统一契约

- 响应：`{ success: true, data, message, timestamp }`（全局 `TransformInterceptor`）；错误：`{ success: false, error: { code, message, details } }`（全局 `HttpExceptionFilter`），生产环境 `details` 收敛为错误码集合。
- 参数校验：DTO 定义于 shared（Zod schema）→ 后端 `zod-nest` 风格管道校验，非法输入 422 + 字段级 details。
- 分页约定：`?page=1&pageSize=20`，响应 `{ items, total, page, pageSize }`；列表统一支持 `q`（名称模糊）等过滤参数。
- API 文档：`@nestjs/swagger` 自动生成 OpenAPI（部署后 `/docs` 可访问，仅非生产开放）。

### 5.3 认证设计（JWT 双令牌）

```
注册 → 发验证邮件（email_tokens, type=verify, 15min TTL）
     → 验证通过 → 事务：users.email_verified_at + 创建 tenants + memberships(role=owner)
登录 → 校验 bcrypt(cost≥12) → 签发：
     ├─ accessToken  15min  payload: { sub: userId, tenantId?, type: 'access' }  Authorization 头
     └─ refreshToken 30d    httpOnly cookie（SameSite=Strict, Secure）          可吊销（服务端存表）
刷新 → 校验 refresh 有效性 + 未吊销 → 轮转（旧 refresh 吊销、发新对）
登出 → 吊销当前 refresh + 清 cookie
找回密码 → email_tokens(type=reset, 30min TTL, 单次有效) → 改密后吊销该用户全部 refresh
```

- 登录失败限流：`@nestjs/throttler` 按 IP+邮箱双维度（5 次/15 分钟），超限返回 `RATE_LIMITED`；登录成功记录审计。
- 会话上下文：`AuthGuard` 解析 token → `req.user = { userId, roles[] }`；当前租户由 `X-Tenant-Id` 头提供，**守卫校验该用户在该租户的 membership 存在且 status=active**，否则 403。

### 5.4 多租户隔离（行级，v1 方案 A）

隔离靠「框架强制 + 测试兜底」双保险：

1. **租户守卫（TenantGuard）**：全局守卫解析 `X-Tenant-Id` → 校验 membership → 注入 `req.tenantId`；未通过直接 403，业务代码**永不从请求参数读 tenantId**。
2. **Prisma Client Extension（核心防漏写）**：`prisma.$extends` 拦截 `findMany/findFirst/update/delete` 等查询，凡模型含 `tenantId` 字段即自动合并 `where: { tenantId: req.tenantId }`；租户上下文由 AsyncLocalStorage 贯穿。漏写过滤在扩展层兜住，代码纪律失效也有第二道防线。
3. **越权回归测试**：Supertest 用例矩阵——租户 B 的 token 访问租户 A 的资源/成员/账单/AI 文档/通知，断言 403/404（详见测试计划专项）。
4. **B 方案迁移路径**：schema 隔离不在 v1 实施；预留：Prisma multiSchema 支持 + 迁移脚本按 tenantId 拆库脚本位，文档标注即可。

### 5.5 RBAC 设计

- 角色：`owner / admin / member`（枚举存 memberships.role）。
- 实现：`@Roles('owner')` 装饰器 + `RolesGuard`；权限矩阵常量在 shared 包，与前端 `usePermission` 同源。
- 边界规则：admin 可管理 member、不可改动 owner 与自身不可自降级（防租户无主）；owner 转让需二次确认且目标必须为 active 成员，事务内完成角色互换 + 审计。

### 5.6 订阅状态机与资金三件套（后端核心专项）

**状态机**（`none → trialing → active → past_due → canceled / expired`，单向无回跳）：

```
                  ┌──────── expired（回Free权益）
  trial到期未支付 ─┘
none ──发起试用──▶ trialing ──模拟支付──▶ active ──续费失败──▶ past_due ──3天宽限内成功──▶ active
                                          │                     └──宽限期满──▶ expired
                                          ├──期末取消──▶ canceled（保留至期末→expired）
                                          ├──立即取消──▶ canceled（即时降级）
                                          └──退款──────▶ canceled（即时降级+账单标记已退款）
```

- 实现为显式迁移表（`TRANSITIONS: Record<from, Set<to>>`）+ `SubscriptionService.transition()` 统一入口：校验合法迁移 → 事务内更新 `subscriptions` + 写 `subscription_events`（含幂等键、触发来源、时间）→ 广播事件（通知/审计/权益联动）。非法迁移抛 `SUBSCRIPTION_STATE_INVALID`，且**非法迁移尝试本身是资损监控四类异常之一**。
- 权益解析：`QuotaService.getEntitlements(tenantId)` 读当前订阅映射套餐限额，内存缓存 60s，订阅变更事件主动失效。

**资金三件套**：

| 件 | 实现 |
|----|------|
| 幂等 | `POST /billing/subscribe` 等资金入口强制 `Idempotency-Key` 头；键 = `tenantId:plan:period:channel` 维度（防全表互挡）；流程：查 `payment_idempotency` 命中→直接返回首次结果（含响应快照）；未命中→ `gateway.charge()` → 事务落幂等记录+账单+状态迁移。宽限期并发续费重试天然复用此机制「仅扣一次」 |
| 对账 | BullMQ repeatable job（每日 02:00 UTC）：拉取 `gateway_transactions`（模拟渠道流水）vs `invoices`，差异（金额不符/单边账/状态不符）写 `reconcile_diffs`（pending），支持人工标记 explained；提供 `POST /dev/reconcile/run` 演示触发器 |
| 资损监控 | 检测器四规则：重复入账（同幂等键多条入账）、负金额、状态回跳（迁移表外流转）、对账差异未处理超 24h → 触发告警：写告警通知（站内必达+邮件必发，不受偏好开关限制）+ 告警日志；提供 `POST /dev/alerts/simulate` 演示注入口 |

**MockPaymentGateway（策略模式）**：

```ts
interface PaymentGateway {
  charge(req: ChargeRequest): Promise<GatewayResult>;   // 返回 txn_no、状态
  refund(txnNo: string): Promise<GatewayResult>;
  query(txnNo: string): Promise<GatewayResult>;
  listTransactions(since: Date): Promise<GatewayTxn[]>; // 对账用
}
// Mock 实现：随机/可控失败率（env 开关），流水落 gateway_transactions 表
// 替换真实网关时新增 StripeGateway 实现 + DI 切换，业务层零改动
```

**金额规范**：全链路 Integer（分）；演示标价 Pro ¥29 → `price_cents = 2900`；无小数运算即无浮点误差；唯一舍入点（未来按比例计费时）统一 HALF_UP 并有单测。

### 5.7 AI RAG 管道

```
上传（txt/md/pdf ≤10MB）→ POST /ai/documents（预签名直传 R2 或小文件直传接口）
  → BullMQ ai-ingest 队列：
     1. 下载解析（pdf 用 pdf-parser）→ 文本清洗
     2. 切分：按段落 + 滑动窗口（chunk ~800 tokens，重叠 100）
     3. Embedding：LLM API 批量向量化
     4. 写 ai_chunks（content + embedding vector(1536) + doc_id + tenant_id）
     → 状态 processing → ready（SSE 通知前端停止轮询）/ failed（错误原因）
提问 POST /ai/ask（SSE）：
  1. QuotaService 预检（当月成功次数 < 套餐额度，否则 QUOTA_EXCEEDED_AI）
  2. 问题向量化 → pgvector 检索 top-k=5（余弦相似度，WHERE tenant_id 强制过滤）
  3. 组装 Prompt（系统提示 + 引用片段 + 问题）→ LLM 流式
  4. SSE 转发 token；结束帧返回 citations[{docId, chunkId, score, 摘录}]
  5. 成功才计数（usage 统计口径 = 成功次数），问答记录落 ai_messages
降级：LLM API 失败/超额 → 返回规则模板回复（检索片段拼接 + 提示），标记 degraded
```

- 向量检索 SQL 强制 `tenant_id` 过滤 + ivfflat 索引（演示量级其实顺扫即可，索引为展示工程完整度）。
- 租户隔离专项测试覆盖：租户 B 提问不得召回租户 A 的 chunk。

### 5.8 异步任务（BullMQ 队列清单）

| 队列 | 触发 | 内容 | 重试策略 |
|------|------|------|---------|
| email | 业务事件 | 验证/重置/订阅/告警邮件（nodemailer SMTP） | 3 次指数退避 |
| ai-ingest | 上传后 | 解析切分向量化（见 5.7） | 2 次，失败标记 failed |
| billing-retry | past_due 进入 | 宽限期内每日重试续费（幂等键不变） | 每日 1 次共 3 次 |
| reconcile | repeatable 每日 02:00 UTC | 对账（见 5.6） | 不重试，失败告警 |
| cleanup | repeatable 每日 03:00 UTC | 回收站到期物理删除、审计 >180 天归档删除、过期 email_tokens 清理 | 幂等设计 |

> Upstash 免费档限流注意：Worker 与 API 同进程部署（Nest 内嵌），避免多进程多实例消耗连接配额；仅生产常驻时拆分。

### 5.9 文件上传设计

- 标准流程（≤10MB）：`POST /files/presign`（预检：类型白名单 + 存储配额余量）→ 返回 R2 预签名 PUT URL（15min TTL）→ 前端直传 → `POST /files/complete`（HEAD 校验对象存在与大小 → 元数据入库 files 表）→ 计入存储配额。
- 软删除资源的附件**不释放配额**（口径：含软删除未到期文件）；资源物理删除/回收站清空时同步删除 R2 对象（异步 job）。
- 分片上传（可选增强，不计入 v1）：`createMultipartUpload → 分片预签名 → completeMultipartUpload`，前端切片 ≥5MB 并发 3 路 + IndexedDB 断点状态；接口契约本版冻结（见需求 5.1），实现开关 `FEATURE_MULTIPART=false`。

### 5.10 SSE 实时通道（v1 降级实现）

- 端点：`GET /events/stream`（需认证 + 租户上下文）；NestJS 原生响应流实现，无额外依赖。
- **SseHubService**：内存 Map<tenantId, Set<response>>；事件类型：`notification`（完整实时）、`resource.changed`（提示条+引导刷新，不做内容合并）、`ai.document.ready`、`heartbeat`（30s，Nginx/平台代理超时保护）。
- 与 BullMQ/业务事件解耦：业务侧调 `eventBus.publish(tenantId, event)`，Worker 进程内直接可达（同进程架构）；断线由前端封装自动重连（见 4.5）。
- presence 降级：`memberships.last_active_at`（认证中间件顺手更新，节流 5 分钟）供前端展示「最近活跃」。
- v2 扩展位：Socket.IO 网关模块替换 events 模块，业务事件总线接口不变。

## 附录 A：技术选型论证（评审答疑基线）

> 本节固化主要选型决策与被否选项的理由，供评审答辩与后续维护者参考。原则：**选型为需求服务，不为简历添彩**——每项决策都可回溯到需求文档的具体条款。

### A.1 前端框架：React 19 vs Vue 3（结论：React）

结论先行：差距主要在**生态与市场信号**，不在语言能力——Vue3 能做这个项目，但以下四点按权重排序后 React 胜出：

| 维度 | 权重 | 判定 | 依据 |
|------|------|------|------|
| 中后台组件生态 | ★★★ | React 胜 | AntD/ProComponents 为 React 第一方，ProTable/ProForm/ProLayout 的更新节奏、类型质量均以 React 版为先；**Vue 生态无 ProComponents 同级对等物**（§4.7 的样板代码压降方案在 Vue 下走不通）。Vue 侧 Element Plus / AntDV 可用但提效上限低 |
| AI 流式 SDK | ★★★ | React 胜 | Vercel AI SDK 的 useChat 等 streaming hooks 为 React 优先实现，SSE 逐 token 渲染/中断控制/消息状态开箱即用；RAG 是本项目差异化亮点（需求 5.2），SDK 级支持优于手写 stream 消费 |
| 服务端状态库成熟度 | ★★ | React 胜 | TanStack Query React 版在无限轮询、乐观更新、缓存 key 隔离（本项目「Query Key 含 tenantId」设计）上积累最厚；vue-query 属移植版，边缘场景踩坑资料少 |
| 市场信号 | ★★ | React 胜 | 国内中后台/SaaS 岗位 React 占比更高；作品集第一属性是可读可对标，主流栈降低评审成本 |

Vue 的真实优势（模板开发快、心智负担低、SFC 组织性好）在引入 ProComponents 后基本被抵消；其硬伤（无 ProComponents 对等物、AI SDK hooks 缺位）对本项目是决定性的。

### A.2 前端工程：手动 Vite vs UmiJS vs Next.js（结论：手动 Vite + ProComponents）

| 方案 | 判定 | 理由 |
|------|------|------|
| Next.js | ❌ | 需求文档 3.1 已论证：Cloudflare Pages 纯静态托管下 Next 需 `output: export` 且失去 SSR，等于放弃 Next 的核心价值，白背框架复杂度 |
| UmiJS（@umijs/max） | ❌ | ① 路由/构建/数据流/权限全为框架约定，作品集评审看到的是「会配 umi」而非「懂工程」，八大验证点第一条「前端工程化」失分；② umi 4 对 React 19 支持滞后，版本锚点被框架节奏锁死；③ 其 access/useModel 约定与已定的 Zustand + TanStack Query 设计冲突。若是公司赶工期中后台则反向推荐 umi，但本项目不是 |
| **手动 Vite + ProComponents** | ✅ | 工程骨架（路由分块/双令牌会话/SSE 封装/租户缓存隔离/权限矩阵）全部自有设计，作品集叙事完整；ProComponents 为独立组件库、不依赖 umi，12 屏样板代码量压到 umi 级（§4.7） |

### A.3 状态管理：Zustand + TanStack Query 分层 vs 单库全包（结论：分层）

- 「客户端状态」与「服务端状态」**性质不同**：前者小而同步（会话/UI 态），后者有缓存/失效/重试语义。TanStack Query 专职服务端状态，Zustand 专职客户端状态，是当前 React 社区收敛后的主流分层。
- 否 Redux Toolkit：样板重，异步语义与 TanStack Query 重叠，单人项目收益为负。
- 关键设计依赖此选型：`Query Key = [tenantId, ...]` 的**租户缓存隔离**（§4.3）只有在精细控制缓存 key 的前提下才成立。
- Pinia 不适用（已选 React，见 A.1）。

### A.4 表单与校验：RHF + Zod（结论：契约同源优先）

- Zod schema 定义于 `packages/shared`，前端表单校验与后端 DTO 校验**同一份定义**（契约同源，M1-02 知识点）；RHF 负责渲染层的高性能非受控表单。
- 否 Formik（维护收缩）、否 AntD Form 裸用（校验逻辑被困在组件层，无法与后端共享）。

### A.5 后端：NestJS vs Express vs FastAPI（结论：NestJS）

| 维度 | 判定 | 依据 |
|------|------|------|
| 横切体系 | 决定性 | 多租户守卫、RBAC 守卫、审计拦截器、限流——NestJS 的 Guard/Interceptor/Pipe + DI 体系是本方案 §5.4/§5.5/§5.13 的直接载体；Express 裸写这些等于手搓半个 Nest，且缺乏工程一致性 |
| 与前端技术同构 | 加分 | 全 TS Monorepo，shared 包契约两端复用（§3）；FastAPI 则引入第二语言，契约同源断裂（可用 openapi-codegen 弥补，但多一道生成链路） |
| 团队背景 | 加分 | 作者前端出身，TS 后端学习曲线最平滑 |
| 性能 | 无差异 | 演示级量级下 Express/Nest/FastAPI 均远超需求 |

### A.6 ORM：Prisma vs Drizzle vs TypeORM（结论：Prisma）

- schema 即文档、迁移工作流成熟（`migrate dev/deploy` 纪律，M2-04）；类型安全由 schema 生成，零手工维护。
- **本项目关键依赖**：Prisma Client Extension 是「租户过滤自动注入」第二道防线（§5.4）的实现载体。
- 否 TypeORM：装饰器模型与维护状态问题；否 Drizzle：更轻更 SQL 味，但其 Extension 生态与本项目所需拦截能力不如 Prisma 成熟——此为 2026 时点判断，若评审时有新版本可复核。
- 已知短板（如实记录）：vector 类型需 `Unsupported` + 手写 SQL（§3.3 数据库文档），复杂查询需 `$queryRaw`——演示级可接受。

### A.7 数据库：PostgreSQL + pgvector vs MySQL / 独立向量库（结论：PG 一库双用）

- 业务数据 + 向量检索**同一库**：免一个独立向量服务（Pinecone/Milvus）的运维成本与免费档不确定性；Neon 免费档直接支持 pgvector。
- pgvector 余弦检索在演示量级（<1e5 chunk）性能绰绰有余，IVFFLAT 索引为工程完整度而建。
- MySQL 无向量类型，选它则必须外挂向量库——此路被否。

### A.8 部署：Cloudflare Pages + Render vs Vercel 全家桶 vs 国内云（结论：免备案组合）

- **Vercel 全家桶**（Next/Vercel Postgres/R2 类似物）：与「Vite 静态 + Neon」相比绑定更深，演示作品不需要平台锁定；且本项目刻意拆两个平台以展示部署运维能力（八大验证点第八条）。
- **国内云**（需 ICP 备案）：周期 1–2 周、个人资质流程重，需求文档第 2 章已定「境外免备案」。
- Render 免费档冷启动慢为已知风险（§8），用保活 + 演示前预热缓解，演示级可接受。

### A.9 选型复核机制

- 表内「版本锚点」在 **M1 动工前统一复核**一次（需求文档 3 章约定），此后锁版本直至对应里程碑交付。
- 任何选型变更走需求文档 10.3 的变更评估表，同步更新本附录与 TSD 相应章节。
