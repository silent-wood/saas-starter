# M5-01 状态机思维（订阅生命周期）

> 知识分类：M5 订阅资金域 ｜ 关联里程碑：M5 ｜ 责任视角：后端 / 业务建模

## 1. 这是什么
把「订阅」看成一台**状态机**：状态有限（none / trialing / active / past_due / canceled / expired），只能在允许的边（transition）上迁移（如 trialing→active、active→past_due），**非法迁移一律拒绝**。每次迁移都记一条事件。

## 2. 为什么值得学
- 状态机是所有「订单 / 审批 / 任务流」系统的通用建模方法，掌握后你能设计任何带流程的业务。
- 防止「状态乱跳」这类最隐蔽的 bug（如已取消的订阅突然变活跃、试用直接跳过期）。
- 本项目 v1.1 把订阅完整化，状态机是其中骨架，也是面试能展开讲的点。

## 3. 核心概念
- **有限状态 + 合法迁移表**：显式定义哪些转移允许，其余报错。
- **事件溯源**：每次迁移写 `SubscriptionEvent { from, to, at, reason }`，可复盘、可对账。
- **单向性**：状态只向前流转，禁止回跳（除非明确支持退款重置）。
- **宽限期**：past_due 给 3 天缓冲，期间仍可用；超时转 canceled。

## 4. 在本项目如何落地
- Free / Pro 套餐，注册可进 14 天 trial（trialing）。
- 迁移由明确触发：`startTrial`、`paySuccess`、`invoiceOverdue`、`cancel`、`expire`。
- 用枚举 + 迁移函数集中管理，业务代码不直接改 `status` 字段（杜绝散落赋值）。

## 5. 关键代码示例
```ts
// 合法迁移表（伪代码）
const TRANSITIONS: Record<Status, Status[]> = {
  none:      ['trialing','active'],
  trialing:  ['active','canceled'],
  active:    ['past_due','canceled'],
  past_due:  ['active','canceled','expired'],
  canceled:  [],           // 终态
  expired:   [],           // 终态
};
function transition(sub, to) {
  if (!TRANSITIONS[sub.status].includes(to)) throw new Error('非法迁移');
  recordEvent(sub, sub.status, to);
  sub.status = to;
}
```

## 6. 常见坑
- 业务代码各处直接 `sub.status = 'active'` → 绕过校验，状态机形同虚设；必须经统一函数。
- 忘了记录迁移事件 → 出问题无法复盘、对账困难。
- 并发迁移（同时两笔）→ 需行锁或乐观锁防止重复。
- 宽限期计时靠前端 cron 不准 → 用后端定时任务或日期比对。

## 7. 验收 / 自测清单
