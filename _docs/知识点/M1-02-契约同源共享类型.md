# M1-02 契约同源（共享类型包）

> 知识分类：M1 工程化地基 ｜ 关联里程碑：M1 ｜ 责任视角：全栈 / 接口设计

## 1. 这是什么
把前后端之间的**接口契约（请求/响应结构、枚举、错误码）定义在一处**（本项目是 `packages/shared`），前端与后端都引用同一份类型，接口形状由「口头约定」升级为「编译期保障」。

## 2. 为什么值得学
- 接口不一致是前后端联调 80% 返工的来源；契约同源从根上消除「字段改名后端忘了改前端」。
- 这是「API First」思想的落地：先定契约，前后端可并行开发（前端甚至可先 mock）。
- 作品集里能讲清楚「我如何管理前后端接口一致性」，是工程成熟度的信号。

## 3. 核心概念
- **单一事实源（Single Source of Truth）**：DTO、状态码、业务枚举只在 shared 定义一次。
- **类型复用**：前端用 `AxiosResponse<LoginRes>`、后端用 `class-validator` 装饰同名字段——形状一致。
- **版本演进**：字段增减在 shared 一处修改，编译错误直接暴露调用方。

## 4. 在本项目如何落地
- `packages/shared/src/types/` 放业务类型：用户、租户、资源、订阅、账单等。
- `packages/shared/src/errors.ts` 放统一错误码枚举（前后端共用）。
- 前端 `api client` 与后端 `Controller` 的出入参都 `import` 自 shared。
- 配合 NestJS Swagger，shared 的 DTO 即接口文档来源。

## 5. 关键代码示例
```ts
// packages/shared/src/types/auth.ts
export interface LoginDto {
  email: string;
  password: string;
}
export interface LoginRes {
  accessToken: string;
  refreshToken: string;
  expiresIn: number;
}
// 后端复用同一结构做入参校验与出参，前端复用做请求/响应类型
```

## 6. 常见坑
- shared 只放「纯类型 / 常量」，不要塞运行时逻辑，避免 web/api 构建耦合。
- 若用了 NestJS `class-validator` 的运行时校验类，这些类也要放 shared 并同时被前后端引用。
- 循环依赖：shared 不能反向依赖 web/api。

## 7. 验收 / 自测清单
- [ ] 后端改了 `LoginRes` 字段名，前端编译立即报错
- [ ] 错误码枚举前后端引用同一份，无重复定义
- [ ] 新增一个接口，先在 shared 加类型，再前后端各自实现

## 8. 延伸学习
- 「API First / Contract-First」设计方法
- OpenAPI 作为契约中间格式
- tRPC（另一种契约同源思路：类型即接口）
