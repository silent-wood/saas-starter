# M4-03 配额与计量口径

> 知识分类：M4 AI / RAG ｜ 关联里程碑：M4 ｜ 责任视角：后端 / 产品技术

## 1. 这是什么
给用户设置**资源使用上限**（席位、存储、AI 提问次数），并**精确统计**其已用量，超限时按既定策略处理（拒绝 / 降级 / 提醒）。「计量口径」指：什么算一次使用、按什么周期（日/月）统计、重置时机——这些定义必须明确且前后端一致。

## 2. 为什么值得学
- SaaS 的「权益随套餐联动」（见 M5）必须有计量载体，否则套餐只是摆设。
- 理解「口径」这类产品设计如何落到技术实现：看似简单，边界 case 极多（跨周期、并发、重试算几次）。
- 直接关联需求文档里的「用量与配额看板」「AI 用量额度」。

## 3. 核心概念
- **配额（Quota）**：上限，通常随套餐（Free/Pro）变化，存租户配置。
- **计量（Usage）**：已用量，常按月统计；AI 按「提问次数或 token」计。
- **口径**：一次 AI 问答 = 1 次用量（还是按 token？失败算不算？重试算几次？需明确定义）。
- **超额策略**：硬拒绝 / 软降级（仍可用但提示）/ 临时升配。

## 4. 在本项目如何落地
- `TenantQuota { seats, storageMb, aiQueriesPerMonth }` 随订阅套餐写入。
- `UsageLog` 记录每次消耗；月度聚合看板展示「已用 / 上限」。
- AI 入口先查用量：超限则拒绝并提示升级（同时落「用量超限」事件）。
- 口径集中定义在 shared，避免前后端理解不一致。

## 5. 关键代码示例
```ts
// 用量校验（伪代码）
const quota = await tenant.getQuota();
const used = await usage.countMonthly(tenantId, 'ai_query');
if (used >= quota.aiQueriesPerMonth) throw new BadRequestException('AI 次数已用尽');
```

## 6. 常见坑
- 并发下「查用量→扣减」非原子 → 超卖；需原子计数或行锁。
- 口径没定义清楚 → 前端显示 9/10，后端记成 11/10，对不上。
- 忘记按月重置 → 永久累加，用户永远超限。
- 重试/失败也计入 → 用户白吃亏；明确「成功才计」。

## 7. 验收 / 自测清单
- [ ] Free 用户 AI 次数用尽后明确提示升级
- [ ] 前后端用量数字一致（口径统一）
- [ ] 跨月后用量正确重置
- [ ] 并发请求不会超卖配额

## 8. 延伸学习
- 计量计费系统设计（rate limiting / quota）
- token 计费与模型成本
- 滑动窗口限流算法
