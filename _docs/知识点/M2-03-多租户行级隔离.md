# M2-03 多租户行级隔离（tenant_id 强制过滤）

> 知识分类：M2 认证与多租户 ｜ 关联里程碑：M2 ｜ 责任视角：后端 / 数据架构

## 1. 这是什么
多租户系统的核心安全命题：**一个数据库、所有租户的数据混存，但彼此绝对不可见**。本项目采用「行级隔离」——每张业务表带 `tenant_id` 字段，所有查询强制带上当前租户的 `tenant_id`，A 租户永远查不到 B 租户的数据。

## 2. 为什么值得学
- 这是 SaaS 架构里**最易出重大事故**的地方（越权看到别家数据 = 数据泄露）。
- 体现「隔离靠架构不靠自觉」：不能指望每个开发者都记得加条件，要在框架层强制。
- 对比方案（schema 隔离 / 独立库）的取舍是架构师常考话题。

## 3. 核心概念
- **行级隔离（共享库 + tenant_id）**：成本低、易运维；代价是每条查询都要带租户过滤。
- **强制手段**：用 Prisma Middleware / NestJS Interceptor 在查询前自动注入 `tenantId`，而非手写 where。
- **跨租户越权测试**：安全回归的核心用例（见 C-01 测试策略）。

## 4. 在本项目如何落地
- 登录后 JWT 携带 `tenantId`，请求上下文（AsyncLocalStorage / Request 对象）保存。
- Prisma `client.$use()` 中间件：对 `findMany/create/update/delete` 自动追加 `where.tenantId`。
- 禁止任何绕过中间件的原生 SQL。

## 5. 关键代码示例
```ts
// Prisma 中间件（伪代码）：写操作强制注入租户
prisma.$use(async (params, next) => {
  if (['create','update','delete','findMany'].includes(params.action)) {
    params.args.where = { ...params.args.where, tenantId: ctx.tenantId };
  }
  return next(params);
});
```

## 6. 常见坑
- 漏掉某条查询没带 `tenantId` → 越权。中间件正是为此兜底。
- 用子查询 / 原生 SQL 绕过 ORM → 隔离失效。需代码规范禁止。
- 聚合统计（count/sum）忘了按租户分组 → 数据串了。
- 测试只测「正常拿到自己数据」，没测「拿不到别人数据」→ 越权用例缺失。

## 7. 验收 / 自测清单
- [ ] 租户 A 创建的资源，租户 B 登录后列表为空
- [ ] 直接拿资源 ID 用租户 B 令牌访问 → 403/404（查不到）
- [ ] 中间件自动注入 tenantId，业务代码无需逐处手写
- [ ] 聚合接口按租户隔离统计

## 8. 延伸学习
- 多租户三种隔离策略对比（行级 / schema / 独立库）
- Postgres Row Level Security（RLS）原生方案
- 租户上下文传递（AsyncLocalStorage）
