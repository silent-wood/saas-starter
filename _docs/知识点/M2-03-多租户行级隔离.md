# M2-03 多租户行级隔离（tenant_id 强制过滤）

> 知识分类：M2 认证与多租户 ｜ 关联里程碑：M2 ｜ 责任视角：后端 / 数据架构
> 状态：✅ 已落地（`src/prisma/tenant.extension.ts`、`src/common/middleware/tenant-context.middleware.ts`、`src/common/guards/tenant.guard.ts`，见 `03-多租户行级隔离` 方案）

## 1. 这是什么

多租户系统的核心安全命题：**一个数据库、所有租户的数据混存，但彼此绝对不可见**。

本项目采用**行级隔离**：每张业务表带 `tenant_id` 列，所有查询强制带上当前租户的 `tenant_id`，A 租户永远查不到 B 租户的数据。

关键在于「**强制**」二字——不靠开发者记得写 `where: { tenantId }`，而是在数据访问层自动注入。业务代码漏写，结果依然正确。

本项目实际由三层构成，缺一层就是漏洞：

| 层 | 组件 | 防什么 |
|----|------|--------|
| 1. 上下文 | `TenantContextMiddleware` + `AsyncLocalStorage` | 让「当前是哪个租户」贯穿整条异步链 |
| 2. 准入 | `TenantGuard` | 用户不属于该租户就直接 403，连查询都不发 |
| 3. 兜底 | Prisma Extension `$allOperations` | 业务代码漏写 `tenantId` 时自动补上 |

## 2. 为什么值得学

- 这是 SaaS 架构里**最易出重大事故**的地方。越权看到别家数据不是「功能 bug」，是数据泄露，要报监管的。
- 它体现一个更普适的工程思想：**安全边界要落在架构层，不能落在人的自觉上**。任何依赖「大家记得加过滤条件」的方案，都会在第 N 个新人手里失效。
- 三种隔离方案（行级 / schema / 独立库）的取舍是架构师面试常考点，而「为什么选行级、代价是什么」能答清楚的人不多。

## 3. 核心概念

### 3.1 三种隔离方案与取舍

| 方案 | 做法 | 成本 | 隔离强度 | 适用 |
|------|------|------|---------|------|
| 独立库 | 每租户一个 database | 最高（连接数、迁移 N 次、备份 N 份） | 最强（物理隔离） | 金融、医疗等强合规，租户数少且大 |
| 独立 schema | 每租户一个 PG schema | 中（迁移要遍历 schema） | 强（逻辑隔离） | 租户数中等（几十到几百） |
| **行级（共享表 + tenant_id）** | 一张表，多一列 | 最低（一次迁移） | 靠代码/框架保证 | **绝大多数 SaaS**，租户数多、单租户数据量不大 |

本项目选行级。**代价必须说清楚**：隔离强度完全依赖「每条查询都带 tenant_id」，一次漏写就是越权。所以选行级就必须配套强制注入机制——这正是本文档后半部分的重点。

### 3.2 上下文怎么传：为什么必须是 AsyncLocalStorage

租户 id 从 `X-Tenant-Id` 请求头进来，但真正执行查询的可能是 service 里第 5 层调用的某个方法。三种传递方式：

| 方式 | 问题 |
|------|------|
| 塞进 JWT payload | 一个用户属多租户，切租户要重新签令牌；令牌还会变大（本项目明确不做，见 01 方案 §4.3） |
| 一层层传参 `fn(tenantId)` | 每个函数签名都被污染，改一次要改一整条链路 |
| **AsyncLocalStorage** | 每个请求一个独立存储，任意深度 `getStore()` 就能拿到 |

**为什么不能用一个模块级变量存 tenantId**：并发请求会互相覆盖。A 请求刚设置 `tenantId=A`，B 请求进来改成 `B`，A 后面的查询就串到 B 去了。这类 bug 在压测前几乎发现不了。

`AsyncLocalStorage.run(store, callback)` 把整条后续调用链包在一个「上下文」里，链上任何位置 `getStore()` 拿到的都是本次 `run` 传入的值。Node 的 async_hooks 保证跨 await / Promise 依然有效。

### 3.3 强制注入的两条路：`$use` 已死，用 `defineExtension`

很多人（包括旧版教程）写的是 `prisma.$use()` 中间件：

```ts
// ❌ 在 Prisma 7 里无效 —— 生成 client 上已无 $use 方法
prisma.$use(async (params, next) => {
  params.args.where = { ...params.args.where, tenantId: ctx.tenantId };
  return next(params);
});
```

本项目实测（`grep '$use' src/generated/prisma/`）**Prisma 7.10 的生成 client 里没有 `$use`**，只有 `defineExtension`。`$use` 从 Prisma 5 标 deprecated，后续版本移除，被官方推荐的 client extensions 取代。

所以正确写法是 `Prisma.defineExtension` + `query.$allOperations`：

```ts
Prisma.defineExtension({
  name: 'tenant-scope',
  query: {
    $allModels: {
      async $allOperations({ model, operation, args, query }) {
        // 在这里改 args，再交给 query(args) 执行
      },
    },
  },
});
```

两者能力对等，但 Extension 的类型更严——严到会卡住你，见 §6 的坑。

### 3.4 白名单：不是「全量注入」，而是「按表开关」

一个直觉方案是「所有模型的查询都加 tenantId」。这是错的，会立刻出问题：

- `User`、`Tenant`、`EmailToken`、`RefreshToken` 是全局表，根本没有 `tenant_id` 列，硬加会 SQL 报错。
- `Membership` 有 `tenant_id`，但**必须排除**（原因见下）。

所以必须维护一份白名单，只对「租户内的业务数据」注入：

| 模型 | 是否隔离 | 原因 |
|------|---------|------|
| `AiDocument` / `AiChunk` | ✅ 注入 | 租户知识库，含 `tenant_id` |
| `Membership` | ❌ **刻意排除** | 见下方 |
| `Tenant` | ❌ | 租户主体本身，按 id 定位 |
| `User` | ❌ | 全局认证主体，可属多租户 |
| `EmailToken` / `RefreshToken` | ❌ | 认证域，按 userId 定位 |

**为什么 `Membership` 必须排除**——这是最容易想错的一处：

`TenantGuard` 的职责是「查这个用户在这个租户里有没有 active 的 membership」。但守卫执行的那一刻，租户上下文还没建立——上下文正是靠这次查询才建立起来的。如果 `Membership` 也被强制合并 `tenantId`，守卫的查询会被扩展「加持」一个来自空值或上一个请求的 `tenantId`，导致明明有权也被判成无权（或反过来）。

更本质的理由：membership 是「谁能进这个租户」的**元数据**，不是「租户内的业务数据」。它本身就不该被隔离。

### 3.5 两条注入路径：`create` 走 `data`，其余走 `where`

不同 Prisma 操作的参数结构不同：

- `findMany` / `findFirst` / `update` / `delete` / `deleteMany` → 有 `where`
- `create` → 没有 `where`，只有 `data`
- `createMany` → 只有 `data`

所以不能用 `operation === 'create'` 来判断后改 `args.where`——TS 会因为联合类型里某些成员没有 `where` 而直接报错（`Property 'where' does not exist on type 'AiDocumentCreateManyArgs'`）。

正确做法是**按字段存在性分支**：`'where' in args` 走过滤，否则走 data 注入。

## 4. 在本项目如何落地（真实代码）

### 4.1 上下文容器 + 白名单 + 拦截纯函数

`apps/api/src/prisma/tenant.extension.ts`：

```ts
import { AsyncLocalStorage } from 'node:async_hooks';
import { Prisma } from '../generated/prisma/client.ts';

// 每个请求一个独立存储；并发请求互不干扰
export const tenantContext = new AsyncLocalStorage<{ tenantId: string }>();

// 白名单：只列当前 schema 里真实存在、且含 tenant_id 的业务模型
// 每建一张新的租户表，必须同步把 model 名加进来，否则该表漏隔离（最危险的隐性坑）
const TENANT_SCOPE = new Set(['AiDocument', 'AiChunk']);

/**
 * 核心拦截逻辑。抽成纯函数是为了可测——defineExtension 返回的是函数不是对象，
 * 单测无法从扩展里取出 $allOperations 回调（见坑 3）。
 */
export async function applyTenantScope(params: {
  model?: string;
  args: unknown;
  query: (args: unknown) => Promise<unknown>;
}): Promise<unknown> {
  const { model, args, query } = params;
  const ctx = tenantContext.getStore();
  // 无上下文 / 不在白名单 → 原样放行
  if (!ctx || !TENANT_SCOPE.has(model ?? '')) return query(args);

  const argsObj = args as { where?: unknown; data?: unknown };
  // 读/改/删：合并 where.tenantId（业务代码漏写也兜得住）
  if ('where' in argsObj) {
    const where = (argsObj.where ?? {}) as Record<string, unknown>;
    return query({ ...argsObj, where: { ...where, tenantId: ctx.tenantId } });
  }
  // create / createMany：注入 data.tenantId（业务代码不用传，也不会传错）
  return query({ ...argsObj, data: { ...(argsObj.data as object), tenantId: ctx.tenantId } });
}

export function tenantScopedExtension() {
  return Prisma.defineExtension({
    name: 'tenant-scope',
    query: {
      $allModels: {
        async $allOperations({ model, args, query }) {
          // 委托纯函数：生产与测试共用同一份实现，不会漂移
          return applyTenantScope({ model: model ?? undefined, args, query });
        },
      },
    },
  });
}
```

### 4.2 把扩展挂到 client 上（这里有个 Prisma 7 的坑）

`apps/api/src/prisma/prisma.service.ts`：

```ts
const baseClient = new PrismaClient({
  adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL, max: 10 }),
});

// ⚠️ 是 baseClient.$extends(...)，不是 PrismaClient.$extends(...)
// Prisma 7 的 PrismaClient 是「构造器类」，$extends 是实例方法
export const extendedClient = baseClient.$extends(tenantScopedExtension());
export type ExtendedPrismaClient = typeof extendedClient;

@Injectable()
export class PrismaService implements OnModuleInit, OnModuleDestroy {
  // 不再继承 PrismaClient，只管理 extendedClient 的生命周期
  async onModuleInit() { await extendedClient.$connect(); }
  async onModuleDestroy() { await extendedClient.$disconnect(); }
}
```

**为什么不再 `extends PrismaClient`**：那样会同时存在两个实例（裸 client + 扩展 client），各开一个连接池（各 `max:10`），既浪费连接，又可能让某条代码路径走到裸 client 上、隔离静默失效。全局只留一个连接池。

业务代码注入的是扩展后的 client：

```ts
constructor(@Inject(PRISMA) private readonly prisma: ExtendedPrismaClient) {}
```

### 4.3 建立上下文（中间件）

`src/common/middleware/tenant-context.middleware.ts`：

```ts
@Injectable()
export class TenantContextMiddleware implements NestMiddleware {
  use(req: Request, _res: Response, next: NextFunction) {
    const tenantId = req.headers['x-tenant-id'];
    if (typeof tenantId === 'string' && tenantId) {
      // run() 把后续整条链包进上下文
      tenantContext.run({ tenantId }, () => next());
    } else {
      next();  // 没有头也放行：/auth/* 和 /tenants 不需要租户上下文
    }
  }
}
```

注意这里**只建立上下文、不做校验**。没头就放行是为了不误伤公开接口；真正的拒绝交给守卫。

### 4.4 准入校验（守卫）

`src/common/guards/tenant.guard.ts`（核心逻辑）：

```ts
const tenantId = req.headers['x-tenant-id'];
if (typeof tenantId !== 'string' || !tenantId) {
  throw new ForbiddenException({ code: 'TENANT_MISMATCH', message: '缺少租户上下文' });
}

// Membership 不在白名单 → 这个查询不会被扩展加 tenantId，是干净的全量查询
const membership = await this.prisma.membership.findFirst({
  where: { userId: req.user.sub, tenantId, status: 'active' },
  select: { role: true },
});

if (!membership) {
  throw new ForbiddenException({ code: 'TENANT_MISMATCH', message: '无权访问该租户' });
}
req.userRole = membership.role;  // 供后续 RolesGuard 使用
```

## 5. 关键代码示例（业务侧最终形态）

业务代码写租户内的查询时，**不写 tenantId**：

```ts
// service 里只有业务条件，租户过滤由扩展注入
const docs = await this.prisma.aiDocument.findMany({
  where: { status: 'ready' },
  // 实际执行：WHERE status = 'ready' AND tenant_id = '当前租户'
});

// create 同样不用传 tenantId
await this.prisma.aiDocument.create({
  data: { fileId, uploadedBy: userId },
  // 实际执行会补上 tenant_id
});
```

这条纪律的验收方式是：**在业务 Service 里搜不到手写的 `where: { tenantId }`**。搜到了说明有人不信扩展、绕过去自己写，那就等于放弃兜底。

## 6. 常见坑（本项目实际踩过的）

| 坑 | 现象 | 正确做法 |
|----|------|---------|
| `PrismaClient.$extends(...)` | `$extends` 不存在 | Prisma 7 的 `PrismaClient` 是构造器类，先 `new` 再在实例上 `$extends` |
| 直接改 `args.where` | 类型报错 `'where' does not exist on ...CreateManyArgs` | `args` 是所有操作的联合类型；用 `'where' in args` 收窄，不要靠 `operation` 字符串判断 |
| 想从扩展对象取 `$allOperations` 测 | 取不到，`defineExtension` 返回的是函数 | 把拦截逻辑抽成纯函数（`applyTenantScope`），扩展与测试都调它 |
| `PrismaService extends PrismaClient` 又另外 `$extends` | 两个实例、两个连接池 | 只保留 `extendedClient`，`PrismaService` 只管生命周期 |
| 业务代码注入 `PrismaService` 当 client 用 | 扩展不生效，隔离静默失效 | 统一注入 `@Inject(PRISMA)` 的 `ExtendedPrismaClient` |
| 把 `Membership` 放进白名单 | 守卫查 membership 被污染，鉴权误判 | 元数据表不进白名单 |
| 新表建好后忘了加白名单 | 该表完全没有隔离，最危险（不报错、只悄悄串数据） | 建含 `tenant_id` 的新表时，同一提交内补 `TENANT_SCOPE` |
| 守卫注册成全局但没做豁免 | `/tenants`、`/auth/me` 也要求租户头 → 403 | 加 `@SkipTenant()` 白名单（本项目在 `06-RBAC与审计` 中修复） |

最后两条是「机制正确但装配错」的典型：隔离逻辑本身没问题，坏在全局注册的副作用上。**全局守卫改动一定要跑一遍现有接口回归**，单测覆盖不到装配层。

## 7. 验收 / 自测清单

- [ ] 租户 A 创建的资源，租户 B 登录后列表为空
- [ ] 拿租户 A 的资源 ID 用租户 B 的令牌访问 → 403/404（不暴露存在性）
- [ ] 业务 Service 里搜不到手写的 `where: { tenantId }`（统一由扩展注入）
- [ ] `create` 不需要手传 `tenantId`，落库后该列有正确值
- [ ] 无 `X-Tenant-Id` 访问需要租户的接口 → 403 `TENANT_MISMATCH`
- [ ] 无 `X-Tenant-Id` 访问 `/tenants`、`/auth/me` → 200（`@SkipTenant` 生效）
- [ ] 新增含 `tenant_id` 的表后，白名单同步更新（代码 review 检查项）

## 8. 延伸学习

- PostgreSQL 原生 **Row Level Security（RLS）**：把隔离下沉到数据库，`SET LOCAL app.tenant_id` + policy，连原生 SQL 都绕不过（本项目没用——Prisma + RLS 的迁移与调试成本偏高，但值得知道）
- Prisma 官方「Client extensions」与「Query extensions」文档
- Node `AsyncLocalStorage` 与 async_hooks 的原理（为什么跨 await 还能保持上下文）
- 多租户数据泄露的真实事故案例（搜索 "multi-tenant data leak"），能看到「漏写一个 where」的实际代价
