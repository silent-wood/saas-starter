# M3-03 软删除与审计日志

> 知识分类：M3 存储与异步 ｜ 关联里程碑：M3 ｜ 责任视角：后端 / 合规

## 1. 这是什么
- **软删除**：不真删数据库行，而是打一个 `deletedAt` 时间戳标记，查询时自动过滤掉。数据可进「回收站」恢复。
- **审计日志**：记录「谁、何时、对什么、做了什么」（如删除成员、改套餐），供追溯与合规。

## 2. 为什么值得学
- 这两个是 **B 端系统的标配设计模式**，你作为前端很少接触，却是企业级应用的硬门槛。
- 软删除防止误删致命数据；审计日志既是安全合规要求，也是排查问题的利器。
- 直接呼应需求文档里的「敏感操作留痕」与「回收站（30 天）」需求。

## 3. 核心概念
- **逻辑删除**：`deletedAt DateTime?` 字段；ORM 查询默认 `where deletedAt = null`。
- **全局过滤**：Prisma 中间件 / 作用域自动排除已删除行（避免漏写）。
- **审计表**：`AuditLog { actorId, tenantId, action, targetType, targetId, meta, createdAt }`。
- **拦截器 / 装饰器**：用 NestJS Interceptor 自动在写操作后落审计，而非业务代码里散落 `log()`。

## 4. 在本项目如何落地
- 业务表统一加 `deletedAt`；Prisma Middleware 让 `findMany/delete` 默认软删、过滤已删。
- 回收站页面列出 `deletedAt != null` 的资源，支持 30 天内恢复。
- 敏感动作（成员移除、owner 转让、订阅取消、配额变更）走 `@Audit()` 装饰器自动记录。

## 5. 关键代码示例
```ts
// Prisma 软删中间件（伪代码）
if (params.action === 'delete') {
  params.action = 'update';
  params.args.data = { deletedAt: new Date() };
}
// 查询自动过滤已删除：
if (params.action === 'findMany') params.args.where = { ...where, deletedAt: null };
```

## 6. 常见坑
- 忘记软删后查询仍要过滤 → 中间件统一管理最稳。
- 唯一约束冲突：软删后同名再建 → 需 `(tenantId, name, deletedAt)` 部分唯一或业务校验。
- 审计日志记太多无关操作 → 噪声大；只对敏感动作审计。
- 审计日志本身被误删 → 审计表应不可软删、只追加。

## 7. 验收 / 自测清单
- [ ] 删除资源后列表消失，但库里行还在（deletedAt 有值）
- [ ] 回收站能恢复 30 天内资源
- [ ] 敏感操作在审计表有可追溯记录
- [ ] 普通查询默认不返回已删数据

## 8. 延伸学习
- 软删除的代价（索引膨胀、唯一约束处理）
- 审计日志与合规（SOX / 等保）
- 事件溯源（Event Sourcing）作为更彻底的方案
