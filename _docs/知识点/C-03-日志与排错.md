# C-03 日志与排错方法论

> 知识分类：横切（贯穿全程）｜ 关联里程碑：全程 ｜ 责任视角：全栈 / 运维

## 1. 这是什么
建立**结构化日志**习惯与一套**系统化排错流程**：出了问题能从日志快速定位，而不是「加 console.log 到处试」。这是后端/运维最基本的生存技能。

## 2. 为什么值得学
- 你作为前端，排错多靠浏览器 DevTools；后端服务在远程，你**看不见**运行现场，只能靠日志。
- 掌握「日志分级、上下文、链路追踪」思维，是从「本地能跑」到「线上可维护」的关键。
- 作品集里能讲「我如何排查线上问题」，是很加分的工程成熟度信号。

## 3. 核心概念
- **结构化日志**：输出 JSON（含时间、级别、tenantId、traceId、消息），便于检索，而非纯文本。
- **日志级别**：debug / info / warn / error，生产只看 warn+，排错临时开 debug。
- **上下文关联**：每个请求带 `traceId`，跨服务/跨函数串起同一请求链路。
- **排错流程**：复现 → 看日志定位层 → 缩小范围 → 假设验证 → 修复 → 加监控防复发。

## 4. 在本项目如何落地
- NestJS 用 `Logger` 或 pino；日志带 `tenantId`、请求 `traceId`。
- 关键路径（登录、支付、AI）打 info；异常打 error 并含上下文（哪个租户、哪个操作）。
- 排错清单：先看部署平台日志 → 再看 DB 迁移是否跑 → 再看 Secrets 是否配对 → 再看 CORS/限流。

## 5. 关键代码示例
```ts
// 结构化日志（伪代码）
this.logger.error('订阅处理失败', {
  tenantId, orderId, stage: 'charge', err: e.message
});
// 排错：按 tenantId + orderId 检索，定位到 charge 阶段
```

## 6. 常见坑
- 只打 `console.log` 无级别无上下文 → 线上大海捞针。
- 把敏感信息（密码、token）打进日志 → 泄露；日志需脱敏。
- 日志量爆炸（每条请求打全量 payload）→ 成本与噪声；按需分级。
- 出错只返 500 无日志 → 无法复盘；error 必带可定位的上下文。

## 7. 验收 / 自测清单
- [ ] 日志是结构化 JSON 且含 tenantId/traceId
- [ ] 日志无明文密码/token
- [ ] 出错有 error 级记录含上下文
- [ ] 有可操作的排错 checklist（部署/迁移/Secrets/CORS）

## 8. 延伸学习
- pino / winston 日志库
- 分布式追踪（OpenTelemetry / traceId）
- 可观测性三支柱：日志 / 指标 / 链路
