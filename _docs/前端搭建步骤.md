## 1. 步骤 1：Monorepo 根骨架

> **本步骤产出 5 项，全部位于仓库根目录下（下文路径均相对于仓库根，即本项目的 `saas-starter/`）：**

|   |   |   |   |   |
| - | - | - | - | - |

> | # | 路径                                     | 类型 | 小节  |
> | - | -------------------------------------- | -- | --- |
> | 1 | `apps/web/src/`、`packages/shared/src/` | 目录 | 1.1 |
> | 2 | `package.json`                         | 文件 | 1.1 |
> | 3 | `pnpm-workspace.yaml`                  | 文件 | 1.2 |
> | 4 | `turbo.json`                           | 文件 | 1.3 |
> | 5 | `.gitignore`                           | 文件 | 1.4 |
>
> **路径基准**：本步骤 4 个文件都在**仓库根**，不在 `apps/web/` 或 `packages/shared/` 里——这是最容易建错位置的地方（根 `package.json` 与 `apps/web/package.json` 同名）。  
> 后续步骤的路径写法：带 `apps/web/` 或 `packages/shared/` 前缀的，相对**仓库根**；不带前缀的（如 §3.6 的 `.prettierrc.json`）相对**所在包根**，各小节标题已注明包根。  
> 本步骤**不创建** `apps/web/package.json`（步骤 3.1）、`packages/shared/package.json`（步骤 2.1）。

### 1.1 目录与包管理

先建目录（两个包根此刻都是空壳，内容分别在步骤 2、步骤 3 填充）：

```bash
cd saas-starter
mkdir -p apps/web/src packages/shared/src
```

创建 **`package.json`**（仓库根，非某个包内）：

```json
{
  "name": "saas-starter",
  "private": true,
  "type": "module",
  "packageManager": "pnpm@11.15.0",
  "engines": { "node": ">=22.22.0" },
  "scripts": {
    "dev": "turbo run dev",
    "build": "turbo run build",
    "preview": "turbo run preview",
    "lint": "turbo run lint",
    "typecheck": "turbo run typecheck",
    "test": "turbo run test"
  },
  "devDependencies": {
    "turbo": "2.11.10"
  }
}
```

> `private: true` 必须有，否则 pnpm 拒绝 workspace 根（知识点 M1-01 坑点 1）。  
> `packageManager` 字段锁定 pnpm 版本，CI 与本地一致。  
> 根 `package.json` 的 `scripts` 全部走 `turbo run`，**不要**在这里直接写 `vite`/`tsc`——那是 `apps/web/package.json` 的职责。

### 1.2 pnpm-workspace.yaml（注意 pnpm 11 的写法变更）

创建 **`pnpm-workspace.yaml`**（仓库根）：

```yaml
packages:
  - "apps/*"
  - "packages/*"

allowBuilds:
  esbuild: true
  prisma: true            # 后端：Prisma CLI 下载 query engine
  "@prisma/client": true  # 后端：Prisma client 生成相关
  "@swc/core": true       # 后端：unplugin-swc 的原生二进制
  "@node-rs/bcrypt": true # 后端：预编译 bcrypt 二进制
```

> **pnpm 11 变更**：旧版 `onlyBuiltDependencies` / `neverBuiltDependencies` 已全部移除，改用 `allowBuilds` 映射（键为包名，值为 `true`/`false`）。  
> 写在 `package.json` 的 `pnpm` 字段里会被忽略并告警，**只有 `pnpm-workspace.yaml` 生效**。  
> 若安装时报 `ERR_PNPM_IGNORED_BUILDS`，执行 `pnpm approve-builds` 交互勾选后把生成的配置提交进版本库。  
> `prisma` / `@prisma/client` / `@swc/core` / `@node-rs/bcrypt` 四项是**后端 `apps/api` 需要的**（见《后端实施指南》§1.2），一次写全免得后端开工时再改。  
> `packages` 两项的 glob 决定了 pnpm 认哪些包为 workspace 成员——**改目录名必须同步改这里**，否则 `workspace:*` 依赖解析失败。


### 1.3 turbo.json（字段是 `tasks`，不是 `pipeline`）

> **为什么用 turbo，而不是只用 pnpm workspace？**
>
> 两者职责不同、不冲突：**pnpm workspace 管依赖**（`packages/*` 之间怎么引用、`node_modules` 怎么装），**turbo 管任务**（多个包之间谁先谁后、结果如何缓存、能否并行）。turbo 是叠在 pnpm 之上的**可选加速层**，不是替代品。
>
> 本项目的理由有两条，都在于**前后端要一起在同一个 monorepo 里构建**：
>
> 1. **依赖拓扑排序**。`@saas/shared` 是 `@saas/web` 与 `@saas/api` 的共同依赖，构建时须先 build shared、再 build 两个 app。只靠 pnpm，得手写 `pnpm --filter @saas/shared build && pnpm --filter @saas/web build && ...` 这样的串联命令，包一多就要人工维护顺序；turbo 的 `dependsOn: ["^build"]` 自动算拓扑，`turbo run build` 一条命令按依赖顺序全量构建。
> 2. **缓存复用**。turbo 按文件指纹缓存任务结果，没改动的包直接命中缓存跳过，只重跑受影响的部分——对「改一下 shared、前后端都要重编」的场景收益明显。
>
> **代价与边界（如实说）**：turbo 引入了一个额外工具、一份 `turbo.json`、一个要锁的版本号。如果只有前端单包、短期单人开发，这份收益很小，**可以先不装 turbo**，用 pnpm `--filter` 手动串联即可；本步骤默认装了，是**默认「前后端一起走」的路线**（后端指南会用到 `turbo run dev` 同时拉起前后端 dev server）。若确定砍掉，删除本文件、并把根 `package.json` 的 `turbo run` 脚本改成 pnpm `--filter` 版本即可。
>
> 版本说明：`turbo` 当前只有 2.x 主线（`latest` 即 `2.11.10`，2026-10-20 发布，无 3.x），**没有大版本取舍**，装 latest 即可；唯一要避开的是网上旧博客的 1.x 配置（`pipeline` 字段已在 2.x 改名为 `tasks`）。

创建 **`turbo.json`**（仓库根）：

```json
{
  "$schema": "https://turborepo.dev/schema.json",
  "tasks": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "typecheck": { "dependsOn": ["^build"] },
    "lint": { "dependsOn": ["^build"] },
    "test": { "dependsOn": ["^build"], "outputs": [] },
    "dev": { "cache": false, "persistent": true },
    "preview": { "cache": false, "persistent": true },
    "clean": { "cache": false }
  }
}
```

> turbo 2.x 已把 1.x 的 `pipeline` 改名为 `tasks`。沿用旧博客的 `pipeline` 配置会直接报 `Found 'pipeline' field instead of 'tasks'`。  
> `preview` / `clean` 两个 task 是为后端 `apps/api` 预留的（后端指南 §1.3 会用到）：`preview` 服务 `vite preview`，`clean` 供 `pnpm clean`（api 的 clean 要同时删 `dist` 与 `src/generated/prisma`）。  
> 根 `turbo.json` 只声明**任务编排**，`name` / `command` / `outputs` 的具体值在各包自己的 `package.json` 里——turbo 按 task 名自动匹配同名的 script。

## 2. 步骤 2：packages/shared 契约包

契约同源是本项目的核心工程主张（知识点 M1-02），前端与后端引用同一份类型与校验。

### 2.1 packages/shared/package.json

```json
{
  "name": "@saas/shared",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "exports": { ".": "./src/index.ts" },
  "scripts": {
    "build": "tsc -p tsconfig.build.json",
    "typecheck": "tsc --noEmit"
  },
  "dependencies": { "zod": "4.6.7" },
  "devDependencies": { "typescript": "6.0.3" }
}
```

> `exports` 直接指向 `src/index.ts`（源码级引用），免去「改 shared 要重装/重建」的问题，Vite 直接编译 TS 源码。代价是 NestJS 侧需用 ts-node/tsc 编译策略——若后端要求 dist 产物，把 `exports` 改为条件导出即可。

### 2.2 packages/shared/tsconfig.json

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,
    "skipLibCheck": true,
    "noEmit": true
  },
  "include": ["src"]
}
```

> **逐字段说明**（这是基础配置，供编辑器 / `tsc --noEmit` 类型检查用，不产出任何文件）：

|   |   |   |   |
| - | - | - | - |

> | 字段                 | 值         | 作用                                           |
> | ------------------ | --------- | -------------------------------------------- |
> | `target`           | `ES2022`  | 编译目标语法版本，与前后端运行时（Node 22 / 现代浏览器）对齐          |
> | `module`           | `ESNext`  | 输出 ESM 模块语法，交给 Vite / ts-node 做后续打包          |
> | `moduleResolution` | `bundler` | 模块解析策略，与 Vite 一致，支持 `exports` 字段与无扩展名导入      |
> | `strict`           | `true`    | 开启全部严格检查（含 `null`/`undefined` 严格区分），契约包类型必须严 |
> | `skipLibCheck`     | `true`    | 跳过 `.d.ts` 声明文件的类型检查，避免第三方库类型报错拖慢检查          |
> | `noEmit`           | `true`    | 只做类型检查、不生成 JS 文件——本包源码由 Vite 直接编译，无需自产 dist  |
> | `include`          | `["src"]` | 只检查 `src/` 目录                                |

### 2.3 packages/shared/tsconfig.build.json

```json
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "noEmit": false,
    "declaration": true,
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": ["src"]
}
```

> **逐字段说明**（这是构建配置，供 `pnpm build` 里的 `tsc -p tsconfig.build.json` 产出 `dist/`，**给后端 NestJS 用**）：

|   |   |   |   |
| - | - | - | - |

> | 字段            | 值                   | 作用                                          |
> | ------------- | ------------------- | ------------------------------------------- |
> | `extends`     | `"./tsconfig.json"` | 继承基础配置的全部 compilerOptions，只覆盖下面 4 项         |
> | `noEmit`      | `false`             | 反向覆盖——基础配置禁止产出，这里要真正生成 JS 文件                |
> | `declaration` | `true`              | 同时生成 `.d.ts` 类型声明文件，后端消费 `dist` 时才有类型提示     |
> | `outDir`      | `dist`              | 编译产物输出目录（前端直接引用源码、后端引用这里的产物）                |
> | `rootDir`     | `src`               | 指定源文件根，保证 `dist/` 内目录结构与 `src/` 对齐（不会多一层嵌套） |

> **前端 vs 后端两套消费方式**：前端 `apps/web` 通过 `exports: { ".": "./src/index.ts" }` 直接编译源码（见 §2.1，无需 dist）；后端 `apps/api`（NestJS）走 `tsc -p tsconfig.build.json` 编译出的 `dist/` 产物。所以本包**同时需要**这两个 tsconfig：`tsconfig.json` 管日常类型检查，`tsconfig.build.json` 管给后端出产物。

## 5. 步骤 5：入口与 Provider 装配

`apps/web/src/main.tsx`：

```tsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { RouterProvider } from "react-router";
import { ConfigProvider, App as AntdApp } from "antd";
import zhCN from "antd/locale/zh_CN";
import { router } from "@/app/router";
import "@/styles/global.css";

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 30_000,
      retry: 1,
      refetchOnWindowFocus: false,
    },
  },
});

createRoot(document.getElementById("root")!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <ConfigProvider locale={zhCN} theme={{ token: { colorPrimary: "#1677ff", borderRadius: 6 } }}>
        <AntdApp>
          <RouterProvider router={router} />
        </AntdApp>
      </ConfigProvider>
    </QueryClientProvider>
  </StrictMode>,
);
```

装配顺序对应 TSD §4.1：`QueryClientProvider → RouterProvider → ConfigProvider(zhCN) → App 全局错误边界`。  
`antd` 的 `App` 组件必须包在 `ConfigProvider` 内，用于承载 `message` / `notification` / `Modal` 静态方法的上下文（antd 5.13+ 起静态方法脱离上下文会报警告）。

`apps/web/src/styles/global.css`（唯一全局样式入口，`main.tsx` 只 `import "@/styles/global.css";` 一次）：

```css
@import "tailwindcss/utilities";
@import "antd/dist/reset.css";

html,
body,
#root {
  height: 100%;
  margin: 0;
}
body {
  font-family: -apple-system, "PingFang SC", "Microsoft YaHei", sans-serif;
}
```

> **统一样式入口约定**：
> - 用 `@import "tailwindcss/utilities"`（仅 utilities 层），**不要**写全量 `@import "tailwindcss"`——全量含 preflight，会与 `antd/dist/reset.css` 双重 reset 冲突，典型症状是 antd `Button` 等组件样式丢失。
> - ⚠️ Tailwind 指令**必须留在 `.css` 里**：若写进 `.less`，Vite 会先用 less 编译器解析 `@import "tailwindcss"`，把它当成磁盘相对路径去找而报错。所以全局入口固定为 `global.css`，不要改成 `global.less`。
> - `src/styles/variables.less` **只服务于组件级 `.less` 文件**，通过 `vite.config.ts` 的 `additionalData` 自动注入，**不进本入口**。
> - antd 主题色在 `main.tsx` 的 `ConfigProvider theme.token` 里配置（见上），与 less 变量各自维护、手动对齐，不要互相依赖。

## 6. 步骤 6：路由与页面骨架

`apps/web/src/app/guards/RequireAuth.tsx`（守卫组件独立成文件，避免与路由对象混在一个文件）：

```tsx
import type { ReactNode } from "react";

export function RequireAuth({ children }: { children: ReactNode }) {
  return <>{children}</>;
}
```

`apps/web/src/app/router.tsx`（先落地两条路由打通链路，12 屏在 M2–M5 逐步填充）：

```tsx
import { lazy, Suspense } from "react";
import { createBrowserRouter, Navigate } from "react-router";
import { Spin } from "antd";
import { LoginPage } from "@/pages/LoginPage";
import { DashboardPage } from "@/pages/DashboardPage";
import { RequireAuth } from "@/app/guards/RequireAuth";

const ResourcesPage = lazy(() => import("@/pages/ResourcesPage"));

const router = createBrowserRouter([
  { path: "/login", element: <LoginPage /> },
  {
    path: "/app",
    element: (
      <RequireAuth>
        <DashboardPage />
      </RequireAuth>
    ),
    children: [
      { index: true, element: <DashboardPage /> },
      {
        path: "resources",
        element: (
          <Suspense fallback={<Spin />}>
            <ResourcesPage />
          </Suspense>
        ),
      },
    ],
  },
  { path: "/", element: <Navigate to="/app" replace /> },
]);

export { router };
```

**路由导入约定**（锁 react-router 7.18.4 的原因之一）：

| 用途                                                          | 从哪导入                                           |
| ----------------------------------------------------------- | ---------------------------------------------- |
| `createBrowserRouter` / `Navigate` / `Link` / `useNavigate` | `react-router`                                 |
| `RouterProvider`                                            | `react-router`（7.x 主入口已导出）或 `react-router/dom` |
| 组件                                                          | 全部从 `react-router` 导入                          |


> 不要写 `react-router-dom`——那是 v6→v7 的兼容垫片，v8 已删除该包，提前用会形成迁移债。

**路由表全量（TSD §4.1，后续按里程碑填充）**：

## 9. 步骤 9：产物体积与后续待办

### 9.1 体积基线（实测）

上述配置下的首次构建产物：

| chunk                             | 原始       | gzip   |
| --------------------------------- | -------- | ------ |
| antd（含 ProComponents + icons）     | 1,760 KB | 569 KB |
| index（含业务代码 + antd 运行时依赖）         | 146 KB   | 45 KB  |
| react（含 react-dom + react-router） | 102 KB   | 34 KB  |

**antd chunk 超过 500 KB 警戒线**，Vite 会告警。这是把 antd 整包打进一个 manualChunk 的必然结果。M1 阶段可接受（演示级不设硬指标），但要在此记录，改进方向有两条：

1. **拆包**：把 `@ant-design/pro-components` 与 `antd` 分成两个 chunk，避免所有页面都被 antd 阻塞；
2. **按需引入**：AntD 6 默认支持 CSS 变量与组件级按需，配合 `import { Button } from "antd"` 的 tree-shaking，把 `manualChunks` 中的 antd 项去掉，改由 Vite 自动分包。

M6 上线前按 TSD §4.8 要求实测 LCP/CLS 并打印体积报告再定稿。

## 10. 常见坑速查

| 症状                                                  | 根因                                | 处置                                       |
| --------------------------------------------------- | --------------------------------- | ---------------------------------------- |
| `Found 'pipeline' field instead of 'tasks'`         | turbo 1.x 配置                      | 改名 `tasks`                               |
| `ERR_PNPM_IGNORED_BUILDS`                           | pnpm 11 默认拦截构建脚本                  | `pnpm approve-builds` + 提交 `allowBuilds` |
| `pnpm` 字段里的 `onlyBuiltDependencies` 不生效             | pnpm 11 已移除该字段                    | 改 `pnpm-workspace.yaml` 的 `allowBuilds`  |
| `TS5101: 'baseUrl' is deprecated`                   | TS 6 废弃 baseUrl                   | 删 baseUrl，`paths` 用 `./src/*`            |
| `TS2882: CSS side-effect import`                    | 缺 vite/client 类型                  | tsconfig `types` 加 `vite/client`         |
| `TS2769: 'test' does not exist in UserConfigExport` | 从 `vite` 导入 defineConfig          | 改从 `vitest/config` 导入                    |
| 测试报 `matchMedia is not defined`                     | jsdom 未实现                         | test-setup.ts 补 mock                     |
| 测试报 `Cannot find package '@testing-library/dom'`    | RTL 的 peer 未装                     | 显式加 devDep                               |
| ESLint 报 `Cannot find package '@eslint/js'`         | flat config 依赖未声明                 | 显式加 devDep                               |
| antd 样式错乱 / 双树告警                                    | 同时装了 pro-components v2 子包与 v3 单体包 | `pnpm why @ant-design/pro-form` 检查，只留单体包 |
| `z.string().email is not a function`                | zod 4 移除该方法                       | 改顶层 `z.email()`                          |
| `Cannot find module 'react-router-dom'`             | v8 已删除该包                          | 从 `react-router` 导入                      |
| antd 静态方法不生效                                        | 缺 `<App>` 包裹                      | ConfigProvider 内加 `App` 组件               |
| 类型不同步（改了 shared 前端不报错）                              | shared 未被引用或未重装                   | 确认 `exports` 指向源码 + `pnpm install`       |
