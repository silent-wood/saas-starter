# 功能技术方案（目录说明）

按**功能点**组织的技术方案，一篇文档覆盖一个功能从需求到测试的全链路。与按端组织的文档正交，不重复它们的内容。

## 与既有文档的分工

| 文档 | 回答什么 | 本目录如何对待 |
|------|---------|--------------|
| `../需求文档.md` | 做不做、给谁做、业务范围 | 只引用章节，不复述 |
| `../技术方案设计.md` | 为什么这么选（架构与选型） | 引用对应章节（如 §5.3 认证设计） |
| `../数据库设计与数据字典.md` | 表结构定义 | 只写本功能新增/变更的字段 |
| `../前端开发规范.md` | 代码怎么写 | 引用，不重写规范 |
| `../后端实施指南.md` | 从零怎么搭 | 引用，不重写步骤 |
| `../测试计划与用例.md` | 全局测试策略 | 只列本功能的用例矩阵 |
| `../知识点/` | 原理讲解 | 遇到关键技术点直接链过去 |

**纪律：引用不复制。** 本目录只写「这个功能特有」的内容。

## 命名与编号

- 文件名：`NN-功能名.md`，两位序号，从 `01` 开始递增
- 不用 `M2-01` 这类里程碑编号——`知识点/` 已占用该格式，同号不同义会混淆
- 一个功能 = 一条能独立验收的用户路径。不要拆到「登录」「登出」各一篇
- 单篇超过约 400 行，或本身含多个子流程（订阅状态机、RAG）时，升级为目录：`03-订阅与支付/{index,前端,后端}.md`，拆的是子流程，不是前后端

## 写文档前：先出决策清单

**方案文档不是提问的地方。** 提不出决策内容的稿子只会变成 TODO 集合，写的人填不上、看的人不敢签。所以顺序固定为：

```
需求 → 决策清单（对话里，不落文件）→ 用户确认 → 写 NN-xxx.md（即定稿）→ 开发
```

决策清单每行写成三列，一次性列全，不要挤牙膏：

```md
| 编号 | 问题 | 推荐 | 不定的后果 |
|------|------|------|-----------|
| D-01 | 未验证邮箱重复注册怎么处理 | 覆盖密码 + 重发验证邮件，返回 201 | 影响 §2 分支与 e2e 用例拆分 |
```

判定标准：**这个点定错要不要返工？** 要返工（接口形状、表结构、错误码、鉴权方式、会话策略）就必须进清单；只影响实现细节（变量名、循环写法）的，自己定，不问。

清单确认后写文档，**决策结论直接落进正文对应小节**（验收标准、异常表、关键约束、测试矩阵），不留决策编号表，也不设「未决项与风险」章节。

## 文档模板

新功能复制以下骨架。前后端写在**同一篇**的 §3 / §4，不拆文件——契约、异常码、时序图都是跨端的，拆开必然不同步。

```md
# NN 功能名

> 版本 v1.0 ｜ 更新 YYYY-MM-DD ｜ 状态：已确认
> 确认：李顺 · YYYY-MM-DD ｜ 变更：—
> 关联：《需求文档》§x、《技术方案设计》§x
>
> 一页速览
> 接口：METHOD /path · METHOD /path
> 前端落点：pages/Xxx、shared/api/xxx
> 后端落点：src/modules/xxx/{controller,service}.ts
> 关键异常：CODE_A / CODE_B

## 1. 需求
### 1.1 用户故事
### 1.2 验收标准（编号 AC-01…，必须可断言）
### 1.3 范围外（明确不做什么）

## 2. 交互逻辑
### 2.1 主流程时序图（Mermaid sequenceDiagram）
### 2.2 分支流程图（Mermaid flowchart）
### 2.3 异常分支表：触发条件 → HTTP → 错误码 → 前端表现

## 3. 前端改动
### 3.1 现状（已有什么）
### 3.2 待改动（文件级）
### 3.3 错误码 → 文案映射

## 4. 后端接口
### 4.1 接口清单（方法/路径/入参/出参/状态码/鉴权）
### 4.2 数据模型变更（表/字段/索引/迁移文件）
### 4.3 关键约束（事务边界、限流、审计、安全）

## 5. 测试
### 5.1 单测
### 5.2 e2e 用例矩阵（正常/边界/异常/越权）
### 5.3 手工验证清单
```

### 验收标准的写法

「注册功能正常」不算标准，无法判定完成。「未验证邮箱登录返回 400 + `EMAIL_NOT_VERIFIED`」才算。每条标准都应该能直接翻译成一条测试用例；反之，§5 里出现没有对应 AC 的用例，说明需求漏写了。

### 图的写法

统一用 Mermaid（IDE 与 GitHub 直接渲染，纯文本可 diff、可 review），不产出 PNG。交互链路用 `sequenceDiagram`，把浏览器 / 前端状态 / API / DB / 外部服务全部画进去；条件分支用 `flowchart`。

## 状态机与确认记录

```
决策清单 → 已确认 v1.0 → 实现中 → 已实现
                        ↘ 变更需求 → 升版本（v1.1…），回到「已确认」
```

- **决策清单未确认时，不建文档、不动业务代码**，这是本流程唯一的卡点
- 方案落盘即定稿（状态「已确认」），不产出带 TODO 的草案。仅当用户明确要求「先出个稿看看」时才用「草案」，且不得据此开发
- 确认后在文档头部记一行：`确认：李顺 · YYYY-MM-DD`，避免口头确认后无据可查
- 开发中方案要改：先改文档升版本，再改代码。**不允许代码先行、文档事后补**
- 全部测试通过后改「已实现」，并补一节「实际与方案的偏差」，把偏离如实写下来

## 豁免清单

**必须写方案**：新功能、接口契约变更、数据模型变更、权限 / 多租户相关、跨端联动。

**直接做，不写方案**：纯 bug 修复、样式与文案调整、依赖升级、注释补充、测试补充。

这条清单是为了让流程活得久。一旦小改动也要走完整流程，人就会开始偷偷跳过，然后整个流程失效。
