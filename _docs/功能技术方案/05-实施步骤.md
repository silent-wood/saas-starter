## 第 1 步 数据层：`invites` 表

改 `apps/api/prisma/schema.prisma`。

**枚举**

```prisma
enum InviteStatus { pending  accepted  revoked }
```

不设 `expired`：过期靠 `expiresAt` 现算。落成状态就需要定时任务去刷，而任务本身又要处理「刷之前一刻用户刚好点开链接」的竞态。

**模型** `Invite`（列名全部 `@map` 成 snake_case）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `String @id @default(cuid())` | |
| `tenantId` | `String @map("tenant_id")` | |
| `email` | `String @db.VarChar(254)` | 与 `users.email` 同口径（RFC 5321 上限） |
| `role` | `MemberRole @default(member)` | 只能是 admin / member |
| `tokenHash` | `String @unique @db.VarChar(64)` | 只存 sha256 hex |
| `status` | `InviteStatus @default(pending)` | |
| `invitedBy` | `String @map("invited_by")` | |
| `expiresAt` | `DateTime @map("expires_at")` | 创建/重发时刻 + 7 天 |
| `acceptedAt` / `acceptedBy` | 可选 | 接受时写入，用于追溯 |
| `createdAt` / `updatedAt` | | |

关系三条，**两条指向 `users` 的必须显式命名**（否则 Prisma 报歧义）：

```prisma
tenant   Tenant @relation(fields: [tenantId], references: [id], onDelete: Cascade)
inviter  User   @relation("InviteInviter", fields: [invitedBy], references: [id])
accepter User?  @relation("InviteAccepter", fields: [acceptedBy], references: [id])
```

反向关系记得补全：`User.sentInvites` / `User.acceptedInvites` / `Tenant.invites`。

索引 `@@index([tenantId, status])`（成员页按租户取待接受）、`@@index([email])`。

**不要**建 `@@unique([tenantId, email])`：那样 accepted / revoked 的历史行也算进唯一性，第二次邀请同一个邮箱直接撞约束。「同一邮箱只有一条 pending」由 service 查重保证（见第 4 步 `upsertPendingInvite`）。

**命令**（两条，`generate` 不是 `migrate` 的副产物保障）

```bash
pnpm --filter @saas/api exec prisma migrate dev --name member_invites
pnpm --filter @saas/api exec prisma generate
```

**自证**：库里 `invites` 三条索引齐全；`schema.prisma` 的 diff 除本步内容外没有别的表被动过（`prisma format` 会重排文件，提交前先看 diff）。

## 第 2 步 契约（shared）

新增 `packages/shared/src/contracts/member.ts`，`index.ts` 补一行 `export *`。

八个导出：

| 名字 | 用途 |
|---|---|
| `memberItemSchema` / `MemberItem` | 成员行（含 `isSelf`） |
| `inviteItemSchema` / `InviteItem` | 待接受邀请行（含现算的 `expired`） |
| `memberListResultSchema` / `MemberListResult` | `{ members, invites }` |
| `createInviteInputSchema` / `CreateInviteInput` | `{ email, role }` |
| `createInviteResultSchema` / `CreateInviteResult` | `inviteItem` + `joinUrl` |
| `invitePreviewSchema` / `InvitePreview` | `/join` 页预览 |
| `acceptInviteInputSchema` / `AcceptInviteInput` | `{ token }` |
| `updateMemberRoleInputSchema` / `UpdateMemberRoleInput` | `{ role }` |

**五条先想清楚的约定**（它们决定后面两端怎么写）

1. **role 一律不含 `owner`**：邀请和改角色只能 admin / member。owner 是 `tenants.ownerId` 上的唯一指称，能邀请出第二个 owner，转让接口的前提（唯一 owner）就失效了。
2. **`isSelf` 由后端算**：前端不知道当前 userId（access token 的 `sub` 没落到 store），自己拿 userId 比必然比错。
3. **接受邀请的 token 放 body 不放路径**：路径会进 access log 与审计 `detail.path`，等于把可兑换的凭证写进日志（06 方案 AC-11）。
4. **`acceptInviteResult` 直接复用 `tenantListItemSchema`**：前端拿到就能 append 进 `['tenants']` 缓存再切换，不用回查 `GET /tenants`（与 `POST /tenants` 同款约定）。
5. **不新增错误码**：`MEMBER_STATE_INVALID` / `OWNER_TRANSFER_INVALID` / `ROLE_DENIED` / `TOKEN_INVALID` 都在 `errors.ts` 里，直接引用。

> zod 必须写 `import * as z from 'zod'`。默认导入会让生成的 `.d.ts` 里出现 `z.z.core.$strip` 这类限定名，消费方（尤其 `moduleResolution: bundler`）拿不到 `z` 成员，`z.infer` 整体退化成 `any`，而且被 `skipLibCheck` 静默吞掉——编译不报错，运行时才发现类型没了。

**自证**：`pnpm --filter @saas/shared build`；两端 `tsc --noEmit` 能解析到新类型。

## 第 3 步 邮件通道上移 `common/mail`

1. `git mv apps/api/src/modules/auth/mail.service.ts apps/api/src/common/mail/mail.service.ts`（保历史）
2. 新增 `common/mail/mail.module.ts`：`providers/exports` 各一个 `MailService`，**不加 `@Global`**——只有真发信的模块才 import，避免「哪个 service 都能发信」的隐式依赖扩散
3. 加 `sendInviteEmail(to, { tenantName, inviterName, joinUrl })`
4. `auth.module.ts`：`imports` 加 `MailModule`、`providers` 去掉 `MailService`；`auth.service.ts` 与 `auth.service.spec.ts` 的 import 路径跟着改

**邀请邮件失败只 log 不抛**，与验证/重置邮件相反。原因：`joinUrl` 会随 `POST /invites` 响应返回，管理员可以复制转发；邮件失败让接口 500，等于把唯一一次拿到明文 token 的机会也一起弄没了。

邮件正文里的「7 天内有效」与 service 的 `INVITE_TTL_MS` 必须同源：两边各写常量，互相注释指向对方。

**自证**：后端能起；注册流程仍能收到验证邮件（devMode 看终端）。

## 第 4 步 `modules/members`

四个文件 + 模块注册。

| 文件 | 内容 |
|---|---|
| `members.module.ts` | `imports: [MailModule, AuthModule]`（要 `TokenService`）；`controllers: [MembersController, InvitesController]`；`providers: [MembersService]` |
| `actor.ts` | `actorFrom(req)` → `{ userId: req.user.sub, role: req.userRole }`；拿不到 role 直接 403 |
| `members.controller.ts` | `GET /members`、`PATCH /:id`、`POST /:id/disable`、`POST /:id/enable`、`DELETE /:id`、`POST /:id/transfer-owner` |
| `invites.controller.ts` | `POST /`、`POST /accept`、`GET /:token`、`POST /:id/resend`、`DELETE /:id` |

`app.module.ts` 的 `imports` 加 `MembersModule`。

**鉴权口径（最容易混的一处）**

- 管理侧（邀请/重发/撤销/改角色/禁用/启用/移除/转让）：租户上下文 + `@Roles('owner','admin')` + `@Audit(...)`；转让额外收紧为 `@Roles('owner')`
- 接受侧（`GET /invites/:token`、`POST /invites/accept`）：`@SkipTenant()`，**绝不能标 `@Roles`**——`@SkipTenant` 下 `req.userRole` 恒 `undefined`，RBAC 一律拒绝（fail-closed），表现为「接口永远 403」，且日志里看不出原因
- `GET /members` **不标** `@Roles`：member 也要能看通讯录，写拦截在另外几个接口上

**service 的三条纪律**

1. `memberships` / `invites` **不在租户扩展白名单**里（`TenantGuard` 查 membership 时还没有租户上下文），所以每个查询都要显式 `tenantId`。漏一处不报错，只是多返回几行——这就是跨租户越权。统一走 `requireTenantId()`，取不到 fail-closed。
2. 对象级规则在 service 判，不塞进 `@Roles`：`@Roles` 只回答「admin/owner 能不能进这个接口」，判不了「目标是不是 owner」。
3. 令牌只存 sha256，明文只在创建/重发的响应与邮件里出现一次（与 `email_tokens` 同纪律）。

**`assertOperable` 的判定顺序**（顺序错了提示会误导用户）

1. 目标是自己 → 409「不能对自己执行该操作」。**先判这个**，否则 owner 操作自己会撞「目标是 owner」，提示牛头不对马嘴
2. 目标是 owner → 409：改角色给 `OWNER_TRANSFER_INVALID`（引导去转让），禁用/移除给 `MEMBER_STATE_INVALID`（转让解决不了「我要禁掉他」）
3. `admin` 操作 `admin` → 403。同级互降会让两个 admin 互相锁死

**`acceptInvite` 的分支顺序**

| 顺序 | 判断 | 结果 |
|---|---|---|
| 1 | token 查不到 / `revoked` / 租户已删 | 410 `TOKEN_INVALID` |
| 2 | membership 已 `active` | **200 幂等**返回 `TenantListItem`（重复点链接不该报错） |
| 3 | membership `disabled` | 409（禁用只能管理员解除，邀请不能绕过） |
| 4 | invite 已 `accepted` 但 membership 没了 | 410（被移除后又点旧链接 → 让管理员重发） |
| 5 | 已过期 | 410 |
| 6 | 其余 | 事务写两条：membership（有 removed 行就 `update`，没有才 `create`）+ invite 置 `accepted` |

`transferOwner` 的三条写入必须同事务：`tenants.ownerId` + 目标 `role=owner` + 原 owner `role=admin`。分开写中途失败会得到「两个 owner」（都能删租户）或「零个 owner」（失去转让起点）。

**自证**：`tsc` 通过；起服务后 `GET /members` 未登录返回 401——单测抓不到依赖注入装配问题，只能靠真正起一次。

## 第 7 步 前端

顺序：api 封装 → 成员页 → 邀请弹窗 → `/join` → 清菜单。每步都可以单独 `tsc`。

1. **`shared/api/member.ts`**：11 个方法的薄封装，类型全从 `@saas/shared` 拿，不重复定义字段。错误由 `client.ts` 归一成 `ApiError`，调用方按 `code` 分支。
2. **`pages/app/members/page.tsx`**：两块 `ProTable`——「成员」（active/disabled）与「待接受的邀请」（pending），后者为空时整块不渲染（空表头只会让人以为哪里出错了）。
   - `canOperate(record)` 是 `assertOperable` 的前端镜像：自己 / 目标 owner / admin 动 admin 三种情况置灰。镜像的意义是**让没权限的按钮直接灰掉，而不是点了才 403**
   - 角色列：owner 渲染 `Tag` 不给下拉（owner 只能通过转让变更，给下拉点完必然 409）；其他给 `Select`，`disabled` 同时看 `can('member.role_change')` 与 `canOperate`
   - 移除用 `Popconfirm`，文案写清「立即失去访问权限，可再次邀请」；转让用 `modal.confirm`（破坏性且不能自助回滚）
3. **`InviteModal.tsx`**：邮箱 + 角色两字段；成功后**不关窗**，切到「链接已生成」态展示 `joinUrl` + 复制按钮。
   - 结果用 `useState` 存而不是 `mutation.data`：再次打开弹窗要能退回表单态，而 `mutation.data` 会一直留着上一次的结果
4. **`_guarded/join/page.tsx`**：三态（正常 / 410 失效 / 409 邮箱不匹配）+ 无 token 兜底；未登录由 `RequireAuth` 带 `returnTo` 拦到登录页，所以这里只管已登录
   - 加入成功后先 `setTenants([...过滤掉同 id, 新团队])` 再 `switchTenant`：`switchTenant` 只改 id 不清列表，缺这行头像下拉会渲染成空
   - `retry: false`：失效类错误重试没意义，只会让用户多等三轮
5. **删 `pages/app/invite/`**（`git rm -r`）。约定式路由下删目录即删路由，但还要同步删 `app/routes/icons.tsx` 的 `invite` 图标与 `app/routes/types.ts` 里 `IconName` 的对应成员——图标是联合类型，漏改 `tsc` 会报
6. **`_guarded/select-tenant/constants.ts`**：邀请说明改成「打开邀请链接即可加入」

**自证**：`tsc --noEmit`；手动打开两个页面看空态。

- 提交后复跑一次 `--force`：lint-staged 会对暂存文件跑 `eslint --fix` + `prettier`，改写后的代码没被验证过

## 第 10 步 端到端自测

完整清单见方案 §5.3，重点两条：

1. 邀请一个**未注册**邮箱 → 隐身窗口注册（填团队名）→ 验证邮箱 → 打开链接 → 加入 → 落到新团队，头像下拉出现两个团队
2. 禁用某人 → 他的下一个请求 403 并自动回落到自己的团队（走 04 的 `TENANT_MISMATCH` 兜底，**不需要令牌黑名单**）
