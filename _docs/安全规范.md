## 1. 安全策略清单（静态底座）

> 说明：以下是「通用安全策略」清单。标注 **✅ 已落地** 的给出本项目真实代码；标注 **⬜ 未落地** 的是常见项，本项目暂未涉及或后续里程碑再补，先占位。

### 1.1 认证与会话

| 策略 | 状态 | 说明 |
|---|---|---|
| 密码哈希（bcrypt / argon2） | ✅ 已落地 | 明文密码永不落库，只存哈希。见 §3.1 |

## 2. 常见网络攻击与防范（静态底座）

> 每种攻击：一句话说明攻击原理 → 本项目（或通用）的防范手段。

### 2.1 用户枚举攻击（Account Enumeration）

**原理**：通过响应差异（状态码、文案、耗时）判断某邮箱是否已注册，为后续撞库/钓鱼提供靶子。

**防范**：让「账号不存在 / 密码错误 / 被禁用」三条路径在**状态码、响应体、耗时**上完全一致。

本项目实现（`auth.service.ts`）：

```ts
// 账号不存在时也拿假哈希跑一次 bcrypt.compare，让两条路径耗时一致
private readonly dummyHash = bcrypt.hashSync('timing-equalizer-placeholder', BCRYPT_ROUNDS);

const passwordMatches = await bcrypt.compare(
  input.password,
  user?.passwordHash ?? this.dummyHash,  // 不存在 → 用假哈希兜底
);
if (!user || !passwordMatches) {
  throw new UnauthorizedException({
    code: ERROR_CODES.UNAUTHORIZED,
    message: '邮箱或者密码不正确',  // 与密码错、被禁用同一个文案
  });
}
// 被禁用也返回同一个 401，不区分
if (user.status !== 'active') {
  throw new UnauthorizedException({ code: ERROR_CODES.UNAUTHORIZED, message: '邮箱或密码不正确' });
}
```

找回密码同理（`forgotPassword`）：邮箱不存在时直接 `return { ok: true }`，静默成功，不写库不发信。

### 2.2 暴力破解（Brute Force）

**原理**：对登录 / 找回密码接口高频试错，穷举弱口令。

**防范**：接口级限流 + 强密码策略 + 高哈希成本。

本项目实现（`auth.controller.ts` + `app.module.ts`）：

```ts
// 登录接口收紧到 5 次 / 15 分钟，覆盖全局默认的 100 次/分
@Public()
@Post('login')
@Throttle({ default: { limit: 5, ttl: 15 * 60 * 1000 } })
// ...
```

```ts
// 全局默认限流：100 次 / 分钟 / IP
ThrottlerModule.forRoot([{ name: 'default', ttl: 60_000, limit: 100 }]),
// 注册为 APP_GUARD 全局生效（走 DI 容器）
{ provide: APP_GUARD, useClass: ThrottlerGuard },
```

> 注意：限流键默认是 IP，若前有 CDN / 反向代理，需读 `X-Forwarded-For` 才能拿到真实客户端 IP（见 C-02 常见坑）。

### 2.3 SQL 注入（SQL Injection）

**原理**：把恶意 SQL 拼进查询字符串，篡改查询语义。

**防范**：永远不手写拼接 SQL，用 ORM 的参数化查询。

本项目实现：全程 Prisma，所有条件走 `where` 对象，由 Prisma 生成参数化 SQL，无字符串拼接。

```ts
// 安全：条件作为参数传入，不会被执行
const user = await this.prisma.user.findUnique({ where: { email } });
```

### 2.4 XSS（跨站脚本）

**原理**：注入恶意脚本到页面，窃取 cookie / 会话（尤其 httpOnly cookie 之外的存储）。

**防范**：三层——cookie `httpOnly`、输出转义、邮件内容可控。

本项目实现（`auth.controller.ts`）：

```ts
res.cookie(REFRESH_COOKIE, token, {
  httpOnly: true,   // JS 读不到，XSS 也偷不走
  sameSite: 'strict',
  secure: this.config.getOrThrow<string>('nodeEnv') === 'production',
  path: REFRESH_COOKIE_PATH,
});
```

> access token 通常存前端内存（不落 localStorage），进一步缩小 XSS 窃取面。

### 2.5 CSRF（跨站请求伪造）

**原理**：诱导已登录用户在不知情下向目标站点发起带凭据的请求。

**防范**：refresh token 走 cookie 且 `sameSite: strict`（跨站请求不携带）；access token 由前端显式加 `Authorization` 头（非 cookie 自动携带，天然免疫 CSRF）。

本项目实现：见 §2.4 的 cookie 配置，`sameSite: 'strict'` 是 CSRF 的主要防线。

### 2.6 SSRF（服务端请求伪造）

**原理**：诱导服务端去请求内网地址 / 任意 URL。

**防范**：服务端发起的请求 URL 一律白名单 / 校验，禁止用户可控地址直连内网。

本项目状态：⬜ 未落地（当前无服务端转发用户 URL 的场景；后续 M4 RAG / 文件下载时需关注）。

### 2.7 文件上传攻击

**原理**：上传恶意文件（可执行、超大、路径穿越）占用资源或触发漏洞。

**防范**：类型白名单、大小限制、重命名存储、隔离域名/权限。

本项目状态：⬜ 未落地（待 M3 对象存储预签名 URL 落地时一并处理）。

### 2.8 令牌重放 / 会话劫持

**原理**：窃取或重复使用有效令牌，冒充合法用户。

**防范**：refresh 轮转 + 落库哈希 + 抢占式消费（一次性令牌）。

本项目实现（`auth.service.ts`）：

```ts
// 抢占式消费：where 带 usedAt:null，并发第二次拿到 count=0 直接失败
const consumed = await tx.emailToken.updateMany({
  where: { id: record.id, usedAt: null },
  data: { usedAt: new Date() },
});
if (consumed.count === 0) throw invalid();
```

### 2.9 越权访问（IDOR / Broken Access Control）

**原理**：直接猜对象 ID 访问不属于自己的资源。

**防范**：资源级鉴权（查归属）、行级隔离（多租户）。

本项目状态：⬜ 未落地（待 M2-03 多租户行级隔离 + TenantGuard）。当前 `/tenants` 已按 `userId` 过滤，但租户内资源的行级隔离待补。

## 3. 本项目安全落地现状

### 3.1 密码哈希

```ts
// auth.service.ts
const BCRYPT_ROUNDS = 12;  // 单次哈希约 200ms
const passwordHash = await bcrypt.hash(input.password, BCRYPT_ROUNDS);
```

### 3.2 令牌只存哈希

```ts
// token.service.ts
createOpaqueToken(): string {
  return randomBytes(32).toString('hex');  // 64 字符，与 VarChar(64) 对齐
}
hashToken(token: string): string {
  return createHash('sha256').update(token).digest('hex');
}
```

### 3.3 access 令牌载荷最小化

```ts
// token.service.ts —— 只放 sub 与 type，不放 email/nickname 等可变信息
signAccessToken(userId: string): Promise<string> {
  return this.jwt.signAsync({ sub: userId, type: 'access' });
}
```

### 3.4 鉴权守卫区分令牌类型

```ts
// jwt-auth.guard.ts —— 防止用 30 天 refresh 长期冒充 access
if (payload.type !== 'access' || !payload.sub) {
  throw this.unauthorized(ERROR_CODES.UNAUTHORIZED, '登录凭证无效');
}
```

### 3.5 环境变量强校验

```ts
// env.schema.ts —— JWT_SECRET 至少 32 位，否则拒绝启动
JWT_SECRET: z.string().min(32),
```

### 3.6 统一错误不泄露内部细节

```ts
// http-exception.filter.ts —— 生产环境不透出 details 字段
details: process.env.NODE_ENV === 'production' ? undefined : details,
```
